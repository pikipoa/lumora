# DESIGN.md — Lumora Design Philosophy

Lumoraは管理ツールではない。
AIとの会話から、未来の自分へ残したい知識を発掘し、育てるためのナレッジOSである。

UIは知識を管理するためではなく、**知識と思考に集中するために存在する**。
画面は機能を主張してはいけない。主役は常に「ユーザーの思考」と「知識」である。

## Design Vision

Lumoraが目指すのは**「静かで洗練されたAI時代のUI」**である。

業務ツールのような管理画面ではなく、Apple・Linear・Arc Browser・Perplexity・Raycastのように、必要なものだけが自然に存在し、触っていて気持ちいい体験を提供する。

## Design Keywords

Minimal / Elegant / Premium / Calm / Focused / Fast / Intentional / Game-inspired / Not childish

ゲームのような世界観は持つが、ゲームUIにはしない。
現実とゲームの境界にあるような、静かなデザインを目指す。

## Core Principles

### 1. Remove Before Add
新しいUIを追加する前に、必ず「消せないか？」を考える。
UIは足し算ではなく、引き算で設計する。

### 2. One Screen, One Purpose
1画面には1つの目的しか持たせない。
ユーザーは「この画面で何をする場所なのか」を3秒以内に理解できなければならない。

### 3. White Space Is UI
余白は装飾ではない。
余白こそが情報を整理する最大のUIである。

### 4. Typography First
アイコンやカードよりも、タイポグラフィで情報を整理する。
文字の大きさ・太さ・余白だけで情報階層を表現する。

### 5. Motion Has Meaning
アニメーションは派手さのためではない。
状態変化を理解するためだけに使う。
速く、静かで、自然であること。

### 6. Progressive Disclosure
最初から全部見せない。
知識が育つほどUIも育つ。
機能は必要になった時だけ現れる。

### 7. One New Word Per Unlock（2026-07-12追加）
ユーザーが1回の解放で出会う新しい固有名詞は**1つまで**。
固有名詞の唯一の教科書は解放演出であり、演出のコピーがその語の定義を兼ねる。
新機能がこの順序を崩すなら、機能側を分割する。
（現在の順序：Search（一般語）→ マーカー（一般語）→ Chronicle → Realm → Wing。
ユーザーが学ぶ固有名詞はこの3つだけ。Arca・Ore・Tagは内部概念でありUIに出さない）

### 8. 名詞は世界観、動詞は日常語（2026-07-12追加）
場所や概念（Realm / Chronicle / Wing）は固有名詞でよい。
しかし操作（検索する・収納する・整理する・戻す）は**絶対に発明しない**。
学習コストの正体はほぼ動詞側にある。
動詞を発明した瞬間、世界観は記憶の補助から学習コストの敵に変わる。

### 9. エラーは、配慮 → 行動 → 必要なら理由（2026-07-28追加）

英語圏のUIは「原因 → 対処」の順で書かれることが多い（"Selection was lost. Please select
the text again."）。日本語でこの順序をそのまま使うと、**理由から入る＝言い訳**と受け取られる。
日本語の自然な接客は次の順序になる。

1. **まず配慮を示す**（すみません／申し訳ありません）
2. **次に、ユーザーがすぐできる行動を伝える**（もう一度テキストを選択してください）
3. **原因は必要な場合だけ、その下に小さく添える**

```
すみません。もう一度テキストを選択してください。
  翻訳・文章校正などのブラウザ拡張機能が原因のことがあります。   ← 必要な時だけ
```

1と2だけでユーザーは行動できる。原因を最初に知る必要は無い。

**内部コードと表示文言は分ける。** 内部では原因ごとにコードを持ち（Sentry・Analytics・
多言語化のため）、ユーザーには復旧方法をシンプルに伝える。**異なるコードが同じ文言に
なってよい** — `selection_lost`と`position_mismatch`の違いはユーザーには意味を持たず、
やることはどちらも「選び直す」だからである（実装：`src/i18n/ja.ts` の`sheetError`）。

**3を付ける基準**：その理由を知らないと、案内した行動を繰り返しても解決しない場合だけ。
拡張機能がDOMを書き換えている時に「もう一度選択してください」だけを出すと、ユーザーは
何度やっても同じ結果に行き着く。逆に、選び直せば直るものに理由は要らない。

この原則は`EVIDENCE-OS.md`の「推測で原因を断定しない」と一致する。断定できない原因を
主役の位置に置かず、ユーザーが確実にできることを先に出す。

## Visual Language

### Avoid

- ❌ Material Design感
- ❌ Android標準UI
- ❌ Bootstrap感
- ❌ 管理画面感
- ❌ カードだらけ
- ❌ 枠だらけ
- ❌ 長文説明
- ❌ アイコン過多
- ❌ 派手なグラデーション
- ❌ 常時表示されるFAB

### Prefer

- ✓ 大胆な余白
- ✓ 少ない色
- ✓ 少ない線
- ✓ 少ない影
- ✓ タイポグラフィ中心
- ✓ 軽いガラス感
- ✓ 滑らかなアニメーション
- ✓ 情報が浮いて見えるレイアウト

### マーカーの重なり — 表示優先順位（2026-07-31追加）

**各文字位置では、その位置を含むMarkerのうち最小区間のみ表示する。**
**表示されない外側Markerも削除されたわけではなく、その区間外では通常どおり表示される。**

長い引用の中の特定語に別の色を引く、という使い方は実在する（実データで4件確認）。
紙の本に色ペンを重ねた時と同じく、**重ねた部分だけ内側の色になる**。新しい記号
（下線・アイコン・件数バッジ等）は一切足さない。

```
外側  ■■■■■■■■■■■■■■■■■■■■■■■■
内側          ■■■■
表示  ■■■■■■■■□□□□■■■■■■■■■■■■
```

**この規則の主語は「文字位置」であって「マーカー」ではない。** ある文字で外側が
表示されないことは、外側のマーカーが消えたことを意味しない。**その文字では代表が
変わっただけ**である。

**色が細かく切り替わることは仕様である。** 3重以上の入れ子では、短い区間で色が
何度も変わりうる。

```
AAAAAA
 BBBB
  CC
→ A B C C B A のように切り替わる
```

これはちらつきや描画バグではなく、**ユーザーが引いた通りに表示している**結果である。
区間をまとめたり、細かい切り替わりを間引いたりしない（間引くと、引いたはずの
マーカーが見えなくなる）。

同じ区間幅のマーカーが競合した場合は、`created_at` → `id` の順で一意に決める
（同値キーには必ず一意なタイブレーカーを付ける。`search-spec.md` 3-6と同じ理由）。

## UX Principles

Lumoraでは**知識が主役**である。
UIは知識の邪魔をしてはいけない。

画面を開いた瞬間、ユーザーは「次に何をすればいいか」ではなく「何を考えようか」と思えること。

## Information Hierarchy

Lumoraでは情報を次の流れで扱う。

```
Search → Marker → Arca → Wing → Realm
```

UIも必ずこの思考の流れを邪魔しないこと。

## Reference Products

| 評価 | プロダクト |
|---|---|
| ★★★★★ | Apple Notes / Arc Browser / Linear / Raycast / Perplexity |
| ★★★★ | Cursor / ChatGPT macOS / Notion |

参考にするのは見た目ではなく、**情報設計・余白・アニメーション・視線誘導**である。

## Implementation Rules

新しい画面を実装する前に、必ず以下を提出すること。

1. ワイヤーフレーム
2. 情報構造
3. 操作フロー
4. なぜこのUIなのか
5. この画面から削れる要素

コードを書き始めるのはレビュー後。

## Definition of Done

UI完成の条件は「動くこと」ではない。以下を満たした時点で完成とする。

- [ ] 初見でも迷わない
- [ ] 余白だけで情報階層が分かる
- [ ] 長時間見ても疲れない
- [ ] 触っていて気持ちいい
- [ ] 他人に見せたくなる
- [ ] 「これ欲しい」と思わせる品質

## 最後に

デザインは目立つために存在しない。
ユーザーが知識に集中し、忘れていた価値ある一文を見つけ、蓄え、育てる。

その体験を邪魔しないことが、Lumoraのデザインである。
