# VISION.md — Knowledge OS

AIチャット統合ナレッジアプリ

---

## 1. 一言でいうと

**AIとの対話を「消費」から「資産」に変えるナレッジOS。**

ChatGPT / Gemini / Claude / Perplexityとの会話を、一時的なチャット履歴としてではなく、長期的に蓄積・検索・整理・再利用できる知識資産として扱うためのプラットフォーム。

---

## 2. 課題認識

1. **チャットタイトルだけでは中身を思い出せない**。重要なアイデアや仕様決定が、埋もれたまま資産化されない
2. **本を読むときのようなマーカー/付箋/メモができない**。「この一文だけ重要」という印を残す手段がAIチャット上に存在しない
3. **AIごとに知識が分散する**。ChatGPT・Claude・Geminiそれぞれで議論した内容が、プロジェクト単位で串刺しに見えない

---

## 3. プロダクト哲学

### 3-1. AI中心ではなく、プロジェクト中心

```
現状：ChatGPT / Claude / Gemini それぞれの中に会話が閉じている
Knowledge OS：プロジェクト → テーマ → AIとの議論、という構造で串刺しにする
```

### 3-2. AIは「意味を推測」できるが、「意味を確定する権利」は人間にある

これがこのプロダクトの核となる思想。

同じ会話でも、AI視点では「受付カウンターUI」と見える内容が、作者にとっては「闘着場という世界観の入口設計」かもしれない。この**差分こそが知識資産の価値**であり、長期プロジェクトにおいて作者本人にしか分からない意味づけを失わないための設計が、このプロダクトの存在意義になる。

このため、AIによるタグ付け・要約生成・重要箇所抽出は、すべて **「提案（proposed）」からスタートし、人間の確定操作を経て初めて資産化される** という一貫したフローを取る（詳細：`ux-flow-and-screens.md`）。却下の履歴も削除せず記録に残し、「AIはこう見たが、自分はそう思わなかった」という判断そのものを将来の資産として保持する。

### 3-3. 情報フローの転換（決定・2026-07-11）：知識の最小単位は「会話」ではなく「マーカー」

Phase1を実データ（Gemini 1178件、Claude 47件）で実際に運用した結果、**当初想定していた情報フローは逆だった**ことが判明した。

**旧フロー（〜2026-07-10）**：`インポート → AI分析（会話全体を要約・タグ付け・マーカー自動発見） → 人間が確認・確定 → Realmへ整理`。この設計は「AIが価値を判断してから人間が確認する」もので、実データ（1000件超）を投入すると「未分類（Inbox）に雑談が大量に並ぶだけで、本当に価値のある知識がどこにあるか分からない」という問題が起きた。

**新フロー（確定）**：
```
インポート → 横断検索でユーザー自身が必要な会話を発掘 → 本文を選択してマーカーを手動作成（＝Arcaへ追加）
→ Arca内のマーカー群に対してのみAIを実行 → AIがタグ付け・分類を行う
```

AIは「発見するAI」ではなく「（人間が選んだ後に）**整理するAI**」に役割が変わる。横断検索は便利機能ではなく、**Lumora最大の価値（知識発掘のコア体験）**である。この転換に伴い、会話ごとのAI要約（Summary）機能とAIによる会話全体からのマーカー自動発見は廃止した。詳細な設計変更は`C:\Users\user\.claude\plans\parsed-enchanting-dream.md`「2026-07-11 マーカー中心アーキテクチャへの転換」を参照。

### 3-4. 本にマーカーを引く体験の再現

蛍光ピンク/グリーン/イエロー/ブルー/レッドという物理的なマーカーの色分けを、AIチャットのテキスト選択メニュー（標準のコピー/切り取りに相当する位置）に組み込む。色の意味づけはシステム側で固定せず、使う人が運用の中で決める。

### 5-3. Phase1で扱わないこと（Non-goals）

- 各AI公式アプリとのリアルタイム同期（技術的に不可能。手動エクスポート→インポートの二段構え）
- Perplexityの一括自動インポート
- 会話と会話の明示的なリンク機能（`ConversationLink`）
- タグ/マーカー色の凡例（レジェンド）機能
- 要約の再生成履歴管理（Phase1は上書きのみ）
- タグの一括承認
- **自動整理（AIによる「アイデア/決定事項/未解決/ボツ案」への分類）**：構想段階のアイデアとして記録のみ。Phase1のタグ/要約/マーカーの枠組みで代替可能かを見極めてから、必要なら別機能として設計する
- **AI間引き継ぎ**（例：Claudeで設計→Geminiで市場調査→GPTで企画整理、と必要な文脈だけを渡してAIを切り替える機能）：構想段階のアイデアとして記録のみ。Phase1のインポート/検索機能が育ってから改めて検討する

## 7. 技術スタック（確定）

| 領域 | 決定 | 理由 |
|---|---|---|
| フロントエンド | React Native (Expo) | おかわり帳と同じ方向性。将来的なApp Store/Google Play配信を最初から見据える |
| バックエンド/DB | Supabase（Postgres + Auth + Storage） | Tag⇄Conversationの多対多、Marker⇄Message等の関係構造はFirestoreよりPostgresと相性が良い。おかわり帳とは意図的に異なる選択（データ構造の性質が違うため） |
| AI処理 | Supabase Edge Functionsからサーバーサイドで各社AI APIを呼び出し、要約/タグ/マーカー生成を非同期ジョブとして実行 | インポート直後の大量処理でタイムアウトしないため |
| 全文検索 | Postgres標準の全文検索機能からスタート | 現状の規模では専用検索エンジン(Meilisearch等)は過剰。必要になってから移行を検討 |
| プッシュ通知 | Expo Notificationsで「レビュー待ち」通知を実装 | Phase1は基本機能として搭載可能。ネイティブアプリを選んだ理由の一つ |

### 既知の技術的リスク：マーカーの範囲調整UI

Web版で想定していた「テキストをドラッグして範囲を微調整→色選択で確定」は、Webブラウザの標準Selection/Range APIを前提にした設計だった。React Nativeにはこれに相当する標準APIが無く、実装難易度が上がる。

対応案（実装着手前に軽い技術検証＝スパイクを推奨）：
- (a) `react-native-gesture-handler`等でテキスト範囲選択コンポーネントを自作する
- (b) 会話本文の表示・マーカー付け機能だけWebView内に実装し、RNシェルとメッセージ通信（postMessage）で完結させるハイブリッド構成にする

どちらを取るかは、Phase1実装順序の⑤（マーカー確定UI）に着手する前に、小さな検証を挟んでから判断する（CLAUDE.mdに実装前提として明記）。

### データの保存場所

会話データ（他社AIとの生ログ含む）はSupabase（Postgres + Storage）にクラウド保存する。プライバシーへの配慮として、外部送信（AI要約生成等のAPI呼び出し）が発生する範囲を明示する設計は引き続きCLAUDE.mdのルールとして維持する。

## 8. ブランド世界観・命名

**アプリ名：Lumora（ルモラ）**
「知識に光を当てるAI時代のナレッジOS」。Lumen(光)+memoria(記憶)のイメージ。

### UI表示名の対応表（最終版）

| データモデル上の名称（変更しない） | UI表示名（ブランド名） | 意味 |
|---|---|---|
| Project | **Realm**（レルム） | 自分が育てる知識領域 |
| Theme | **Wing**（ウィング） | Realm内の棟・区画 |
| Conversation | **Chronicle**（クロニクル） | AIとの思考の旅の記録 |
| Tag/Marker/Summaryの`proposed`状態 | **Ore**（鉱石） | まだ精錬（確定）されていない発見 |
| Tag/Marker/Summaryの`confirmed`/`edited`状態 | **Arca**（アルカ） | 人間が確定して残した宝箱 |
| （Phase2バックログ）AIによる関連発見機能 | **Beacon**（ビーコン） | 過去の知識との関連性をAIが照らし出す機能。下記参照 |

**重要な設計原則**：この命名はUI表示文言としてのみ適用し、データベースのテーブル名・フィールド名（`Project`/`Theme`/`Conversation`/`Tag`/`Marker`/`Summary`/`status: proposed/confirmed`等）は変更しない。ブランド名を将来調整したくなっても、データ構造への影響が出ないようにするため（詳細な実装ルールは`CLAUDE.md`参照）。

**Ore⇄Arcaの物語的な意味**：「AI提案→人間確定」というこのプロダクトの核となる思想が、そのままUI上の言葉として体験できる。「まだOreの状態です」「Arcaに収めました」という表現が、状態遷移の説明を兼ねる。「原石→精錬されて宝物に」というストーリーがArcaと自然に繋がる。

**Beaconの定義について（訂正履歴）**：検討初期には「`proposed`状態のラベル」として案出したが、「Beaconは保存場所や状態ラベルではなく、AIが過去の考えとの関連性を発見して照らし出す機能であるべき」という整理により再定義した。`proposed`状態のラベルは代わりに**Ore**とした。Beaconは以下「9. 機能バックログ」でPhase2機能として扱う。

### タグの世界観

タグは3種類に分かれる（詳細：`data-model.md`）：
- **Topic**（何について）：例 `#ゲーム` `#AI` `#教育`
- **Concept**（何の概念か）：例 `#社会変化` `#パラダイムシフト`。AIの強みが最も発揮される抽象化ラベル
- **Role**（自分の知識内での役割）：💡idea / 🔭hypothesis / 📌decision / ⚔️strategy / 📚learning。固定小選択肢のため`Marker.role_tag`として実装

タグ付けの主戦場は会話（Chronicle）全体ではなく、個々の発見物（Marker）単位。理由：会話のタイトルと内容が話しているうちに変容するケースが多く、会話全体への一括タグ付けでは不正確になるため。

### 体験の設計原則：メカニズム層とブランド層を混同しない

**Layer 1（メカニズム層＝機能語彙のまま）**：Marker（重要箇所の保存）／Tag（分類）／Summary（圧縮理解）／Role（役割）。ここがVISION.mdの技術的な核。

**Layer 2（体験・世界観層＝ブランド名）**：Realm（所属）／Wing（区画）／Chronicle（経緯）／Ore（未確定）／Arca（確定・保存）。

この2層を混同すると「Beaconってタグ？保存場所？検索機能？」のような混乱が起きる（実際に検討中、Beaconの定義自体で一度この混乱が起きた）。Layer1は手段、Layer2は体験、という区別を実装・コミュニケーション双方で維持する。

## 9. 機能バックログ（Phase2以降・設計のみ記録）

### Beacon（AIによる関連発見機能）
AIが「この情報は過去のあなたの考えと関連があります」と関連性を照らし出す機能。単発のタグ生成とは異なり、蓄積されたArca全体を横断した意味的検索（embedding等）が必要になる高度機能のため、Phase1には含めない。Phase1の全文検索（Postgres標準）が育ち、Arcaに十分なデータが蓄積されてから着手する。

**2026-07-11の情報フロー転換により、この機能はより自然な拡張になった**：Arcaが人間の選んだマーカー（＝既に価値判断済みの知識）のみで構成される設計になったため、Beaconが意味的検索の対象にするデータは「玉石混交の会話全文」ではなく「既に厳選されたマーカー群」になる。ノイズが少ない分、Phase2着手時の精度・実装コストの両面で有利になる見込み。

**「AI発見Realm」との関係（2026-07-11、Tag/Wing分離の検討時に浮上）**：Arcaに一定数マーカーが蓄積されたらAIが「これは新しいRealm候補です」と提案する機能は、Beaconとほぼ同種（AIによる関連発見）。Tag/Wing分離の実装ではこの機能を明示的にスコープ外とし、Beaconとの位置づけを整理してから別途着手することにした。着手時はこの節とあわせて設計すること。

### BAS Scan
選択した文章に対し「🔍 BAS Scan」ボタンを押すと、AIが新規性・将来性・関連領域・注意点を評価し、Beacon保存を推奨する機能。**前提条件**：BASは元々「文明監査」を目的としたフレームワークであり、Lumora（個人の知識管理）向けに適合させた別バージョンの設計が完成してから組み込む。現時点ではBAS Scan自体の設計は行わず、「Lumora向けBAS設計」というタスクが先行タスクとして必要であることのみ記録する。

### 入力範囲の拡張（Web記事等）
「読む→発見→Beacon化」という体験は、将来的にはインポートした4社AIチャット以外（Web記事等）にも広げたいという長期的な野心として記録する。**Phase1のスコープは変更しない**（4社AIチャットのインポートのみ）。将来この方向に進む場合、import-spec.mdの対象範囲を再定義する必要がある。
