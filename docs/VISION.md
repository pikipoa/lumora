# VISION.md — Knowledge OS

AIチャット統合ナレッジアプリ

---

## 1. 一言でいうと

**AIとの対話を「消費」から「資産」に変えるナレッジOS。**

ChatGPT / Gemini / Claude / Perplexityとの会話を、一時的なチャット履歴としてではなく、長期的に蓄積・検索・整理・再利用できる知識資産として扱うためのプラットフォーム。

---

### 1-1. Core Vision（構想・仮、2026-07-13）

ピキさんが言語化した、より長期的な方向性。**確定事項ではなく構想として記録する**（既存の「1. 一言でいうと」を置き換えるものではない）。今後Phase2以降の機能（Beacon等）を検討する際の判断軸として参照する。

> 人間の思考を、AI時代に最適な知識資産へ変える。

そのための5つの柱：

| 柱 | 内容 |
|---|---|
| 🧠 外部ワーキングメモリ | 人間の認知負荷を減らす |
| 🔍 知識の発見 | 長い対話から必要な知識を見つける |
| 🧩 知識の構造化 | Arca、Wing、Realmで育てる |
| 🤝 AIとの共通言語 | AIが人間の思考ルールを理解できるようにする |
| 🚀 知識活用 | MD、仕様書、SNS、翻訳など様々な形へ展開する |

**この構想から生まれた最初の実装判断（2026-07-13）**：マーカーの色にユーザー自身が意味（例：🟨根拠／🟦仕様／🟩設定／🩷アイデア／🟥注意点）を登録できる機能を追加する。

**最も守るべき前提（ピキさんの明示的な指示）**：この機能は**「AIのための機能」ではなく「ユーザー自身の思考ルールを言語化・表現する機能」である**。すでに無意識に使い分けている色の運用ルールを、本人が自覚し、言葉にして残すことが第一の目的。AIと意味を共有できることはその副次的な結果に過ぎず、存在理由ではない（Beacon（9章）提案時の手がかりになりうる、という話は「あくまで後から生まれる利点」であって「作る理由」ではない）。この前提はUIの文言・導線設計（例：「AIに教える」ではなく「自分の意味を残す」という言い回しにする等）にも一貫して反映すること。

5-3で「タグ/マーカー色の凡例（レジェンド）機能」として明示的にPhase1 Non-goalに指定していたものと同じ機能だが、この新しい理由付けにより優先度を見直し、Non-goalsから外してPhase1スコープへ格上げする。**Phase1では登録UIとデータ保存のみ**とし、`organize-markers`/`organize-wings`のAIプロンプトへ実際に渡すのはPhase2（Beacon設計時）に回す（詳細：`settings-ia.md`）。

## 2. 課題認識

1. **チャットタイトルだけでは中身を思い出せない**。重要なアイデアや仕様決定が、埋もれたまま資産化されない
2. **本を読むときのようなマーカー/付箋/メモができない**。「この一文だけ重要」という印を残す手段がAIチャット上に存在しない
3. **AIごとに知識が分散する**。ChatGPT・Claude・Geminiそれぞれで議論した内容が、プロジェクト単位で串刺しに見えない

## 3. プロダクト哲学

### 3-1. AI中心ではなく、プロジェクト中心

```
現状：ChatGPT / Claude / Gemini それぞれの中に会話が閉じている
Knowledge OS：プロジェクト → テーマ → AIとの議論、という構造で串刺しにする
```

### 3-2. AIは「意味を推測」できるが、「意味を確定する権利」は人間にある

これがこのプロダクトの核となる思想。

同じ会話でも、AI視点では「受付カウンターUI」と見える内容が、作者にとっては「闘着場という世界観の入口設計」かもしれない。この**差分こそが知識資産の価値**であり、長期プロジェクトにおいて作者本人にしか分からない意味づけを失わないための設計が、このプロダクトの存在意義になる。

このため、AIによるタグ付け・要約生成・重要箇所抽出は、すべて **「提案（proposed）」からスタートし、人間の確定操作を経て初めて資産化される** という一貫したフローを取る（詳細：`ux-flow-and-screens.md`）。却下の履歴も削除せず記録に残し、「AIはこう見たが、自分はそう思わなかった」という判断そのものを将来の資産として保持する。

### 3-3. 情報フローの転換（決定・2026-07-11）：知識の最小単位は「会話」ではなく「マーカー」

Phase1を実データ（Gemini 1178件、Claude 47件）で実際に運用した結果、**当初想定していた情報フローは逆だった**ことが判明した。

**旧フロー（〜2026-07-10）**：`インポート → AI分析（会話全体を要約・タグ付け・マーカー自動発見） → 人間が確認・確定 → Realmへ整理`。この設計は「AIが価値を判断してから人間が確認する」もので、実データ（1000件超）を投入すると「未分類（Inbox）に雑談が大量に並ぶだけで、本当に価値のある知識がどこにあるか分からない」という問題が起きた。

**新フロー（確定）**：
```
インポート → 横断検索でユーザー自身が必要な会話を発掘 → 本文を選択してマーカーを手動作成（＝Arcaへ追加）
→ Arca内のマーカー群に対してのみAIを実行 → AIがタグ付け・分類を行う
```

AIは「発見するAI」ではなく「（人間が選んだ後に）**整理するAI**」に役割が変わる。横断検索は便利機能ではなく、**Lumora最大の価値（知識発掘のコア体験）**である。この転換に伴い、会話ごとのAI要約（Summary）機能とAIによる会話全体からのマーカー自動発見は廃止した。詳細な設計変更は`C:\Users\user\.claude\plans\parsed-enchanting-dream.md`「2026-07-11 マーカー中心アーキテクチャへの転換」を参照。

**検索の役割の再定義（決定・2026-07-13）**：横断検索は「答えを見つけて終わる場所」ではなく、「まだ知識化していない会話からArcaを発掘するための入り口」である。検索の目的・原則・検索対象の基準・フォールバックの考え方・Beaconとの役割分担は`search-spec.md`に集約する（本節は検索の目的・思想のみを扱う。`search-spec.md`自体も具体的なアルゴリズム・SQL実装は対象外とし、実装コード側に委ねる）。

### 3-3-1. 「AIの恩恵が後に来る」設計を弱点に見せない位置づけ（構想・2026-07-26）

`docs/oss-radar.md`の調査で判明した通り、海外のPKM/AI second brain系OSS（claude-obsidian、SwarmVault等）は「データを放り込めばAIが即座に全部リンク・整理してくれる」方式が既に主流になっている。Lumoraの「AI提案→人間確定」は、この主流とは意図的に逆を行くため、**AIの恩恵を受けるタイミングが競合より遅い**という見え方をしうる。これを弱点に見せないための位置づけを以下に整理する。

1. **「遅さ」ではなく「保険」だと言い切る**：Lumoraは実際に「AIが会話全体を自動分析して要約・タグ・マーカーを提案する」方式を2026-07-11以前に採用し、実データで「ノイズが増える」という悪い結果になってやめた経緯がある（本章3-3参照）。つまりLumoraの「遅さ」は単なる慎重さではなく、**一度試して失敗した方式を意図的に避けている**という実体験に基づく判断であり、正面からそう主張できる。全自動リンク方式が抱えるリスク（AIが勝手に作った関連付けを、半年後も信じられるか）は、既にこの章で扱った「6年分のメモを一晩でAIに読ませた」系の記事への懸念（9章「Arca項目の『使われた回数』トラッキング」）とも共通する
2. **「恩恵が後に来る」を欠点ではなく進行システムとして見せる**：9章「音声検索・執事のイメージ」で構想した「Beaconの中身が段階的に育つロードマップ＝やりこみ要素」の考え方がそのまま使える。「最初は地味だが、使うほど自分専用のAIが賢くなる」体験は、"待たされている"のではなく"育てている"という感覚に変換できる
3. **体感の遅さ自体を減らす余地は残っている**：実際のフロー（インポート→検索→マーカーを引く→AIが整理）で本当に負荷が大きいのは最初の数分の印象だけであり、実質的な追加作業は「どうせ検索する」「読んでいる文章に線を引く」程度に収まる。ここは既存の解放演出・Cold Start設計（本章3-5、DESIGN.md）の質をさらに上げることが、"AIを待つ"感覚を消す一番効くレバーになる

**結論**：「弱点に見えないようにする」より、**「これは競合の弱点（全自動リンクが半年後には信じられなくなるリスク）を踏まえた上での意図的な選択だ」と正面から主張する**方が説得力がある。

### 3-5. v2.1 認知OSへの改訂（決定・2026-07-12）：人間の認知順序をそのままUIにする

Lumoraはメモアプリでも知識管理アプリでもなく、**人間が考える順番をそのままUIに変換した認知OS**である。ローカル実運用で「Chronicle・Arca・Realmを独立した画面として並べると、次にどこへ行けばいいか考える場面が発生する」と判明したため、UIと知識フローを認知順序に揃えた：

```
Import → Search → マーカー（＝Arca生成）→ Realm選択 → Realmへ収納
→ AI分析 → Wing候補（確度付き）→ ユーザー承認 → 収納 → Tag（内部）
```

5つの知識オブジェクトの正式定義は`data-model.md`「0. 設計思想」を正とする（Chronicle=文脈／Arca=知識の最小単位＝マーカーそのもの・内部概念／Realm=知識世界・知識編集の中心／Wing=人間の理解構造／Tag=AIの理解構造）。要点：

- **Arcaはマーカーを引いた瞬間に生成される**。AI分析はArcaを作るのではなく意味を付与する工程。ArcaはUIの主役ではなく内部概念（Arca専用画面・ホームカードは廃止）
- **Realm選択はマーカー直後**（人間が「この話は何についてか」を最初に理解する認知順序に一致）。スキップ可能で、未割当分はChronicle先頭の「整理待ち」一時セクションに出る
- **Realmは知識編集の中心**：マーカー本文はRealm内で自由編集できる（Chronicle原文とは独立。原文は不変でAIは元知識を参照可能）
- **AIはWing候補を確度付きで提示するだけ**で、収納の決定は常にユーザー（採用／既存Wing選択／新規Wing作成）
- **Tagは常時表示しないが、レビュー対象からは隠さない**。「AI分析結果を見る」で確認できる。ユーザーがやっているのはタグ編集ではなく「AIがこの知識を正しく理解できているかの確認」

### 3-4. 本にマーカーを引く体験の再現

蛍光ピンク/グリーン/イエロー/ブルー/レッドという物理的なマーカーの色分けを、AIチャットのテキスト選択メニュー（標準のコピー/切り取りに相当する位置）に組み込む。色の意味づけはシステム側で固定せず、使う人が運用の中で決める。

## 7. 技術スタック（確定）

| 領域 | 決定 | 理由 |
|---|---|---|
| フロントエンド | React Native (Expo) | おかわり帳と同じ方向性。将来的なApp Store/Google Play配信を最初から見据える |
| バックエンド/DB | Supabase（Postgres + Auth + Storage） | Tag⇄Conversationの多対多、Marker⇄Message等の関係構造はFirestoreよりPostgresと相性が良い。おかわり帳とは意図的に異なる選択（データ構造の性質が違うため） |
| AI処理 | Supabase Edge Functionsからサーバーサイドで各社AI APIを呼び出し、要約/タグ/マーカー生成を非同期ジョブとして実行 | インポート直後の大量処理でタイムアウトしないため |
| 全文検索 | Postgres標準の全文検索機能からスタート | 現状の規模では専用検索エンジン(Meilisearch等)は過剰。必要になってから移行を検討 |
| プッシュ通知 | Expo Notificationsで「レビュー待ち」通知を実装 | Phase1は基本機能として搭載可能。ネイティブアプリを選んだ理由の一つ |

### 既知の技術的リスク：マーカーの範囲調整UI

Web版で想定していた「テキストをドラッグして範囲を微調整→色選択で確定」は、Webブラウザの標準Selection/Range APIを前提にした設計だった。React Nativeにはこれに相当する標準APIが無く、実装難易度が上がる。

対応案（実装着手前に軽い技術検証＝スパイクを推奨）：
- (a) `react-native-gesture-handler`等でテキスト範囲選択コンポーネントを自作する
- (b) 会話本文の表示・マーカー付け機能だけWebView内に実装し、RNシェルとメッセージ通信（postMessage）で完結させるハイブリッド構成にする

どちらを取るかは、Phase1実装順序の⑤（マーカー確定UI）に着手する前に、小さな検証を挟んでから判断する（CLAUDE.mdに実装前提として明記）。

### データの保存場所

| データモデル上の名称（変更しない） | UI表示名（ブランド名） | 意味 |

**Beaconの定義について（訂正履歴）**：検討初期には「`proposed`状態のラベル」として案出したが、「Beaconは保存場所や状態ラベルではなく、AIが過去の考えとの関連性を発見して照らし出す機能であるべき」という整理により再定義した。`proposed`状態のラベルは代わりに**Ore**とした。Beaconは以下「9. 機能バックログ」でPhase2機能として扱う。

**普遍語への変更は却下、代わりにアイコンで補強する方針に確定（決定・2026-07-22）**：長く使うユーザーにとって固有名詞（Realm/Wing/Chronicle）の学習コストが負担になるのではという懸念から、これらを汎用語へ変更する案を検討したが、却下した（経緯：`rejected-decisions.md`）。理由は、`unlocks.ts`に実装済みの解放演出（DESIGN.md原則7「One New Word Per Unlock」）がRealm/Wing/Chronicleを1つずつ教える設計になっており、汎用語化するとこの演出自体の存在意義が失われるため。代わりに、**名前はそのまま維持し、各名称に象形的なワンポイントアイコンを追加してタイポグラフィを補強する**方針を採用した。DESIGN.md原則4「Typography First」（タイポグラフィが主）とも矛盾しない（アイコンは主役を置き換えず補強するのみ）。

### タグの世界観

タグは3種類に分かれる（詳細：`data-model.md`）：
- **Topic**（何について）：例 `#ゲーム` `#AI` `#教育`
- **Concept**（何の概念か）：例 `#社会変化` `#パラダイムシフト`。AIの強みが最も発揮される抽象化ラベル
- **Role**（自分の知識内での役割）：💡idea / 🔭hypothesis / 📌decision / ⚔️strategy / 📚learning。固定小選択肢のため`Marker.role_tag`として実装

タグ付けの主戦場は会話（Chronicle）全体ではなく、個々の発見物（Marker）単位。理由：会話のタイトルと内容が話しているうちに変容するケースが多く、会話全体への一括タグ付けでは不正確になるため。

### 体験の設計原則：メカニズム層とブランド層を混同しない

**Layer 1（メカニズム層＝機能語彙のまま）**：Marker（重要箇所の保存）／Tag（分類）／Summary（圧縮理解）／Role（役割）。ここがVISION.mdの技術的な核。

**Layer 2（体験・世界観層＝ブランド名）**：Realm（所属）／Wing（区画）／Chronicle（経緯）／Ore（未確定）／Arca（確定・保存）。

この2層を混同すると「Beaconってタグ？保存場所？検索機能？」のような混乱が起きる（実際に検討中、Beaconの定義自体で一度この混乱が起きた）。Layer1は手段、Layer2は体験、という区別を実装・コミュニケーション双方で維持する。

## 9. 機能バックログ（Phase2以降・設計のみ記録）

### Beacon（AIによる関連発見機能・Pro機能として確定）

AIが確定済みの知識（Arca）を材料に、整理・比較・関連付けを行う機能群。単発のタグ生成とは異なり、蓄積されたArca全体を横断した意味的検索（embedding/pgvector等）が必要になる高度機能のため、Phase1には含めない。Phase1の横断検索（`search-spec.md`）が土台として育ち、Arcaに十分なデータが蓄積されてから着手する。**Lumoraの料金モデル（10章）における唯一の有料機能**でもある。

**2026-07-11の情報フロー転換により、この機能はより自然な拡張になった**：Arcaが人間の選んだマーカー（＝既に価値判断済みの知識）のみで構成される設計になったため、Beaconが意味的検索の対象にするデータは「玉石混交の会話全文」ではなく「既に厳選されたマーカー群」になる。ノイズが少ない分、Phase2着手時の精度・実装コストの両面で有利になる見込み。

**検索対象の確定（決定・2026-07-22）**：Beaconの検索対象は**確定済みArcaのみ**とし、未確定（proposed）状態や生の会話全文（Chronicle）は対象に含めない。3-2の核となる思想（AIは意味を推測できるが確定する権利は人間にある）と、7-11転換の教訓（生データを直接AIに読ませるとノイズが増える）の両方を維持するための線引き。あわせて、`Tag`（Topic/Concept、CLAUDE.md「AIが検索・分類のために使う内部メタデータ」）を検索の絞り込みに併用し、embedding単体の意味検索よりも精度の高い候補抽出を行う（実装方式は着手時に設計）。

**Beaconの核はEmbedding/ベクトル検索ではない（設計思想・決定・2026-07-23）**：Embedding/pgvectorは数ある検索技術の1つに過ぎない。Beaconの本質は、**AIが確定済みArcaを材料に自律的に育てる構造化知識ベース（AI理解層）**である。この層はTagと同じ「AIが検索・分類のために使う内部メタデータ」という位置づけの延長線上にあり、Tagが持つ情報（Topic/Concept）を、エンティティ（人物・企業・プロジェクト等）・関係性・根拠（引用元Arca）・信頼度・更新履歴を持つグラフへ発展させたものと捉えられる。

イメージとしては3層構造：
```
人間層（Chronicle/メモ/写真/音声等、人間が書く・持ち込む一次情報）
AI理解層（Entity/Relation/Evidence/Confidence/Timeline。確定済みArcaから自動抽出、AIが自分のために育てる知識グラフ）
検索層（全文検索/Tag/Embedding/グラフ探索。AI理解層へアクセスするための手段の一つ一つ）
```
この位置づけにより、将来Embedding以外の検索技術に置き換わっても（あるいは複数を併用しても）Beaconの設計思想自体は変わらない。「Arca同士の関連発見」「時系列ストーリー生成」（上記想定機能）は、単発の意味的類似検索よりも、この知識グラフを辿ることで初めて自然に実現できる。着手時はTagとの役割分担（Tagは検索・分類、AI理解層は関係性・時系列・根拠までを持つ）を含めて設計すること。

**Pro機能として想定する内容（確定・2026-07-22）**：
- AI検索（Arca限定・自然文クエリ、例：「先月A社と話した価格交渉ってどうなった？」）
- Arca同士の関連発見（「この知識と関連するArcaは？」）
- 時系列ストーリー生成（「この考え方が変化した経緯は？」）
- 判断理由の抽出（「このプロジェクトで重要だった判断だけ並べて」）
- プロジェクト横断分析（「同じテーマのArcaをグループ化」）
- 将来のAI機能全般

**「AI発見Realm」との関係（2026-07-11、Tag/Wing分離の検討時に浮上）**：Arcaに一定数マーカーが蓄積されたらAIが「これは新しいRealm候補です」と提案する機能は、Beaconとほぼ同種（AIによる関連発見）。Tag/Wing分離の実装ではこの機能を明示的にスコープ外とし、Beaconとの位置づけを整理してから別途着手することにした。着手時はこの節とあわせて設計すること。

### Beaconの対話スコープ：Wing/Realm/横断の3段階（構想・2026-07-24）

外部の「第二の脳」トレンド記事（Karpathy言及の3ステップ：取り込む/尋ねる/見直す）をきっかけに、「尋ねる」＝自然文でAIと対話する体験について検討した。結論として、この体験自体は上記Beacon Pro機能リストの「AI検索（Arca限定・自然文クエリ）」と同一であり独立した新機能ではないが、対話の**対象範囲（スコープ）**をどう決めるかという設計はこれまで未検討だった。以下を構想として記録する。

**3段階のスコープ**：Wing限定（今開いているWingのArcaのみ）／Realm限定（今いるRealm全体のArca）／全Realm横断（Arca全体）。ナビゲーション階層（Realm一覧→Realm詳細→Wing）がそのまま対話範囲の階層になる。

**デフォルトはナビゲーション文脈が自動的に決める**：Wingページを開いていればWing限定、Realm詳細ならRealm限定、ホーム等のグローバルな入口からなら全Realm横断がデフォルトになる。設定画面や毎回の選択UIは持たない。

**切り替えは既存chipデザインを流用した1個のトグルのみ**：画面上部に「🔵 このWing/Realmのみ」⇄「🌐 すべて」という小さいピル型トグルを1つ置くだけで、複数選択UI・永続設定は増やさない（DESIGN.md「Remove Before Add」原則）。

**"スマート"は新しいUIでなく、既存トグルへの誘導で表現する**：狭いスコープで確信度が低い/該当が薄いときは、回答の下に「もっと広く探しますか？」という小さな誘導だけを出し、上記トグルをハイライトする。ただしスコープを実際に広げる操作は常に人間の1タップに残す（AIが判断だけで対象を勝手に広げて答えることはしない＝3-2の人間確定原則との整合）。

**速度面の裏付け**：スコープが狭いほどArcaの検索母集団が小さくなり、クエリコストも体感速度も上がる。デフォルトを狭いスコープにすることは精度面だけでなく文字通りの速さにも直結する。

**このモデルが今のUIと異なる点**：現状のRealm/Wing/Chronicle一覧は、静的なリストを人間が読んで辿る「ファイルブラウザ」的なUIである。この構想は「今開いているページがどこか＝AIが見る範囲」というモデルで、ナビゲーション自体が検索スコープを兼ねる。ファセット検索（タグ・フィルタでの絞り込み）で終わらず、絞り込んだ先で自然文の対話に接続する体験として位置づける。

### Beaconの結果画面：ノードマップ＋Navigatorパネル（構想・2026-07-24）

きっかけは外部ツール「Fable」で作られた宇宙・惑星モチーフの思考マインドマップ（クリックするとノードが光り、関連する思考がハイライトされて「回遊」でき、下部のNavigatorパネルで選択項目の詳細を見せる形式）。見た目（宇宙・グロー・惑星のビジュアル）とObsidian Vaultとの自動双方向連携はLumoraには持ち込まない（前者はDESIGN.mdの「派手なグラデーション」回避・本セッションで決めた紺系ダークパレット方針と矛盾する。後者はLumoraがエクスポートファイルの手動アップロード方式のみでライブ同期基盤を持たないこと、および一次情報が「AIとの会話」であり自筆ノートvaultではないことと噛み合わない）。

**構造だけを持ち込む理由**：Beaconの核は元々グラフとして設計済みである（本章「Beaconの本質」：エンティティ・関係性・根拠・信頼度・更新履歴を持つ構造化知識ベース）。データモデルが既にノードと関係性の形をしているのに、UIとしては自然文チャット（「AI検索」）しか設計しておらず、`ux-flow-and-screens.md`にもBeaconの結果画面のUIは存在しない。放射状ノードマップ＋Navigatorパネルは、既存のグラフ構造をそのまま見せる可視化として空白を埋めるものであり、既存の決定を置き換えるものではない。

**採用する形**：ノード間の関係性を放射状に表示し、ノードを選択すると下部（または横）のパネルにそのArcaの詳細（引用元、根拠、確度等）を表示する構造。配色はLumoraの既存ダークパレット（`theme.ts`）をそのまま使い、グロー・グラデーション・宇宙モチーフの装飾は付けない。タイポグラフィ中心・少ない色というDESIGN.mdの原則の範囲内で作る。

**「尋ねる」との関係**：上記「Beaconの対話スコープ」で構想した自然文チャット（尋ねる）と、このノードマップを辿る体験（回遊）は矛盾せず、Beaconへの2つの入り方として共存できる——質問という直線的な入口と、関連性を眺めて寄り道する入口。

### 音声検索・執事のイメージ（構想・2026-07-25）

きっかけは「Lumora〜忘れない記憶」というキャッチコピーを考えていた延長で出てきた着想。ピキさんの例え：**自分のことを自分よりも知っている執事**。人間の執事なら「最初の明確な記録は2025年10月です。ただ、その1か月前から『探索型UI』というアイデアが複数回登場しています。そこが原点かもしれません」と、資料と共に答える。ピキさん自身「MVPとはズレる部分がこのように出てくると思う」と明言しており、Phase1のスコープではなく将来の方向性としての記録。

**シナリオ**：「古着」で検索→1234件→「去年の秋頃だったかな、10月かも」と曖昧な時期を声で足す→AIが9〜10〜11月に解釈して絞り込み→315件→さらにAIが「◯◯関連10件／仕入れ関連20件／マイページ・闘着場関連70件」等の主要な文脈をまとめて提示する、という多段階の会話的絞り込み。

**既存原則との整合を取った採用方針**：
- **時期の曖昧表現→具体的な範囲への変換は、AIが提案しユーザーが1タップで確定する形にする**（構想時点でピキさん同意済み）。`search-spec.md`「検索条件はAIが自動変更しない」という確定原則があるため、AIが黙って条件を書き換えて再検索することはしない。「秋頃、10月ということは9〜11月で探しましょうか？」という提案→確定のステップを挟むことで、原則を守りながら会話的な手触りを保つ
- 315件を用途別にクラスタリングして見せる部分は、横断検索(S8)の機能としては`search-spec.md`「整理後の構造を検索結果に混ぜない」原則と衝突するため、横断検索本体には持ち込まない。この振る舞いは実質的にBeaconの役割（関連発見・時系列ストーリー生成）と重なる
- 音声入力そのもの（キーボードではなく声で検索・絞り込みを行う）は、将来のインターフェースの選択肢として記録するのみで、Phase1の対象ではない
- 「半年後の会議も音声データを取り込んでおけば検索できる」という発展形（音声の取り込み・文字起こし）は、実は`search-spec.md`「2-2」に既にある「将来的な拡張の考え方」（画像OCR・PDF・音声・動画も『一次情報』の原則にそのまま当てはまる）の延長線上であり、突飛な話ではない

**会議利用時の複数人録音（構想・2026-07-25）**：会議では1人が代表して録るより、参加者それぞれが自分のデバイスで自分の声を録った方が、話者ごとの音質・分離精度が上がるのではという着想。**ただし複数人の録音をネットワーク経由で同期・1つの記録にまとめる処理自体はLumoraのスコープ外**とし、別のツールに任せる。Lumoraが受け取るのは、その処理が終わった後の「1つにまとまった記録」を**記憶の参照として**取り込む部分のみ（`search-spec.md`「2-2」の音声取り込みの延長）。これにより、Lumora自体が複数ユーザー間のリアルタイム同期基盤を持つ必要はなく、`infra.md`の「認証必須の個人向けアプリ」という前提や、テーブルが1ユーザーの所有物であるという既存のデータモデル（RLS前提）を変えずに済む。

**発言の個人確認（構想・2026-07-25）**：取り込んだ複数話者の記録のうち「これは自分の発言として文字起こしされた部分です、合ってます」と確認する仕組み。これは新しい多人数協業の仕組みを作るのではなく、**Proposed→Confirmedという既存の人間確定原則を、インポート時の自分の担当部分の確認という形にそのまま当てはめるもの**（CLAUDE.md 2-1）。各参加者は自分のLumoraアカウント内で、自分に該当する部分だけを確認する、という単一ユーザー完結の操作として設計できる。音声そのものを声紋等で識別する処理（「自分の声をAとして登録」）を使うかどうかは、この確認作業の精度を上げる手段の1つとして着手時に検討する（生体情報を扱うため、テキストの会話ログより慎重な設計が必要）。

**未決定事項（意図的に保留）**：執事的な連想（「1か月前から別の言葉で同じアイデアが出ていた」等）の探索対象を、確定済みArcaのみに限定する（Beaconの既存スコープ決定を踏襲）か、生の会話全文まで広げるかは未決定。後者は「生データを直接AIに読ませるとノイズが増える」という2026-07-11の教訓と緊張関係にあるため、着手時に改めて判断する。

**執事の名前はユーザーが自由に決める（構想・2026-07-25）**：Beaconという仕組み・機能名はそのまま保つが、執事という"人格・声"の部分の呼び名はLumora側で1つに固定せず、ユーザー自身が名付けられるようにする。デフォルトの提案候補として以下3つ＋自由記入欄を出す案：

| 候補 | 由来・ニュアンス |
|---|---|
| Familiar（フェミリア） | 魔女や魔法使いに古くから仕え、主人を誰よりも知っている「使い魔」。「自分より自分を知っている」という執事の発想に一番直接的に合う |
| Custos（クストス） | ラテン語で「守護者・番人」。Arca（ラテン語由来）と語源の系統が合い、知識の宝箱を見守る番人のイメージ |
| Warden（ウォーデン） | 「番人・管理人」を意味する平易な英単語。分かりやすいが執事らしい親密さはやや弱い |

この「ユーザーが自分の執事に名前をつける」という発想は、「AIとの思い出アルバム」訴求軸（本章、2026-07-22）で挙がった**存在感**（AIがそこにいるように感じたい）の欲求とも相性が良い。Realm/Wing/Chronicleのような固定の固有名詞（DESIGN.md「One New Word Per Unlock」で1つずつ教える体系語彙）とは性質が異なり、こちらはシステム語彙ではなくユーザーによる個人化なので、既存の解放演出の仕組みとは競合しない。

**料金モデルへの位置づけ（確認済み・2026-07-25）**：Beaconの価格帯自体は分けない。10章の「無料/Proの線引きは機能の多寡ではなく役割の違いで分ける」という原則をそのまま維持し、Pro（Beacon）は単一価格のまま、中身（尋ねる→回遊→音声→執事的な連想）が開発の進行に応じて機能として育っていくロードマップとして扱う。ピキさんの着想：この「使うほど・時間が経つほどBeaconができることが増えていく」という体験は、人によっては**やりこみ要素**（本章冒頭・DESIGN.md「Progressive Disclosure」「知識が育つほどUIも育つ」と同じ思想の、Pro機能版）として楽しめる可能性がある。

### 「AIとの思い出アルバム」訴求軸（構想・2026-07-22）

ピキさんの着想：AIとの関係性を重視する層（例：AI恋人的な使い方をする層）が求めるものは、**記憶**（前に話したことを覚えていてほしい）・**継続性**（続きを自然に話したい）・**存在感**（そこにいるように感じたい）の3つに分解できる。Realmが担うのは主に「記憶」で、「AIと築いた人生を振り返る場所」＝**思い出アルバム**として機能させれば、この層とも相性がある。

**Lumora全体の思想との関係**：この3つの欲求（記憶・継続性・存在感）は恋愛AI層に固有ではなく、Lumoraが元々想定している「長期的にAIと付き合う人」（4章）全般に程度の差はあれ通底する。恋愛AI層はこれを最も強く感じているだけ、と捉えられる。「Realm＝思い出アルバム」という言い換えは、既存の機能（Realm＝知識を育てる場所）の見せ方を変えるだけで説明がつく。

**なぜコードを変えずに読み替えが成立するのか**：データモデル上の名称は今も`Project`（意思決定支援を思わせる、仕事の入れ物という響き）のままだが、UIでは最初から`Realm`という抽象度の高いブランド語に置き換えている（CLAUDE.md「メカニズム層とブランド層を混同しない」8章Layer1/Layer2分離）。これは元々「ブランド名をデータ層に持ち込まない」ための設計判断だったが、結果として`Project`という仕事色の強い言葉が一度もユーザーの目に触れないという副産物を生んでいる。表示名も"Project"のままだったら、「思い出アルバム」という読み替えはずっと不自然だったはず。ブランド語の抽象度を保つこと自体が、対象読者を広げる余地（コードを変えずに複数の意味づけに耐えられること）に直結するという発見。

**Phase1では採用しない（決定・2026-07-22）**：ポジショニングを恋愛AI層まで広げると、現在のペルソナ（4章：開発者・起業家・研究者等、意思決定支援用途）向けの機能語彙（横断検索・Tag・organize-markers）と訴求が薄まるリスクがある。ローンチまで10週間というタイミングでの軸拡大はVISION.mdペルソナ・DESIGN.mdのトーン・オンボーディングコピー全てに連鎖するため見送る。**この着想はローンチ後、マーケティングコピー・訴求軸のテスト（現行の機能・ポジショニングを変えず、伝え方だけ変える実験）としての位置づけに留める**。

**あわせて出た関連アイデア（AIの見た目を写真から再現するキャラクター生成機能、別プロジェクトで企画中）は、Lumoraへの移植を含めて完全にスコープ外**。技術的にも画像生成基盤という別領域であり、他人の写真からAIの「見た目」を生成することには通常の知識管理機能には無いコンテンツモデレーション・肖像権のリスクが伴うため、着手する場合は軽い検討では済まず別途慎重な検討が必要。

### 学習型Wing自動収納（v2.1で予約・2026-07-12）
Wing候補のユーザーレビューが十分に蓄積された段階（目安：100回程度）で、AIが「このユーザーは『UI設計』ではなく『認知OS』へ入れる傾向がある」と学習し、**確信95%以上のものだけ自動収納**する最終形。自動収納した場合も「自動収納しました／元に戻す」を必ず表示する。`marker_wings.confidence`列はこの機能の土台として既に実装済み。Phase1では提案型（ユーザー承認必須）のみ。

### BAS Scan
選択した文章に対し「🔍 BAS Scan」ボタンを押すと、AIが新規性・将来性・関連領域・注意点を評価し、Beacon保存を推奨する機能。**前提条件**：BASは元々「文明監査」を目的としたフレームワークであり、Lumora（個人の知識管理）向けに適合させた別バージョンの設計が完成してから組み込む。現時点ではBAS Scan自体の設計は行わず、「Lumora向けBAS設計」というタスクが先行タスクとして必要であることのみ記録する。

### 個別チャットのURL/PDF取り込み（構想・2026-07-23）

ZIP一括エクスポートより手軽に、公式の「共有」機能で作った単一チャットのURLからも取り込めれば、オンボーディングの障壁を下げられるのではという着想。実際に3社の共有ページを調査（2026-07-23）した結果：

- **ChatGPT**：raw HTMLに会話データが埋め込まれているが、React Router独自のシリアライズ形式で要デコード。実装コスト中
- **Claude**：`/api/chat_snapshots/{id}`という公開REST JSON APIがあり、フィールド名が公式エクスポート（`conversations.json`）とほぼ同一（`chat_messages`/`sender`/`text`/`parent_message_uuid`等）。既存の`parseClaude`をほぼ流用できる見込みで実装コストが低い
- **Gemini**：Google内製の`batchexecute`RPCプロトコル（非公開・複数`rpcid`に分散・頻繁に仕様変更される）で、リバースエンジニアリングの費用対効果が悪い

**推奨方式（決定・2026-07-23）**：共有ページのAPIを直接叩く方式は非公式フォーマットの逆解析に依存し、各社の仕様変更で壊れるリスクが高い（特にGemini）。3社とも共有ページからPDF出力ができるため、**PDF経由の取り込みの方が安定性で優れる**（PDFはより標準化された出力形式で、テキスト抽出は成熟した技術）。ただしPDFパース自体（レイアウト依存のテキスト抽出精度、ページ構造からのuser/assistant発言分離ロジック）は別途実装が必要で、無条件に簡単というわけではない。

**Phase1では見送り（決定・2026-07-23）**：3社とも今回のスコープ外。ローンチ後、オンボーディング改善の一環として着手を検討する。着手する場合はPDF方式を優先的に検討し、共有API直叩き方式（特にGemini）は避ける。

### Arca項目の「使われた回数」トラッキング（構想・2026-07-13）

外部記事（Obsidian設計者Nainsi Dwivedi氏の指摘）からの着想：メモが死ぬのは「集める」と「使う」が分断されているため。Arcaが「開かれない倉庫」に堕落しないための予防策として、「保存した回数」ではなく「後から実際に参照・引用・活用された回数」を測る仕組みが有効ではないか。

**Lumoraの既存思想との整合性の確認**：この着想元の記事は「AIが毎晩自動で仕分けて、使えるメモだけ残す」という設計を提案しているが、これはLumoraの核となる思想（AI提案→人間確定を必ず経る、却下履歴も消さず残す）と逆方向であり、そのままは採用しない。あくまで「使われた回数を可視化する」という計測の発想部分のみを取り入れる。

**具体案（未設計・要検討）**：
- Arca化されたMarker/Tag/Summaryが、後から検索結果としてクリックされた／メモが追記された／他の発見物と関連付けられた等のアクションを記録する
- 一定期間「一度も参照されていないArca項目」を可視化する機能（例：「開かれていない発見物」ビュー）
- 目的はAIによる自動削除ではなく、あくまで人間が「これはもう不要かも」と気づくための気づきの提供に留める（Lumoraの人間確定原則を維持）

**発火の仕組みの具体案（構想・2026-07-24）**：別の外部の「第二の脳」トレンド記事（Karpathy言及の3ステップの1つ「見直す」＝AIが週次で全体を巡回する発想）を検討した際に得た着想。新しい自動化の仕組みをゼロから作るのではなく、既存のOre→Arca確定フロー（`proposed→confirmed/rejected`）を「週次のまとめレビュー」というトリガーで動かすだけで実現できるのではないか。AIが「しばらく参照されていない／孤立していそうなArca項目」を週1回まとめて抽出・提示し、人間が一括で確認（残す/統合する/却下する）する運用にすれば、Lumoraの人間確定原則を崩さずに、この記事とObsidian記事の両方が指摘する「見直しの手間」という本質的な課題に応えられる。さらに別の第三の記事（過去6年分のメモを一晩でAIに読ませた事例）で示された「過去に信じていたことと今書いていることの矛盾を指摘する」という着想も、同じ週次バッチに「孤立していそうなArca」と並べて「過去のArcaと矛盾していそうなArca」を提示する形で乗せられそうで、能動的な提示に留め自動修正はしないという原則もそのまま維持できる。

**トリガー条件**：Phase1でArcaに十分なデータが蓄積され、「見返さない発見物」が実際に増え始めたら着手を検討する。

## 10. 料金モデル（確定・2026-07-22）

> 無料で「知識を育てる」。有料で「育った知識と対話する」。

この一文がLumoraの事業モデルの核。無料/Proの線引きは機能の多寡ではなく、**知識化の入口（生成）と知識の活用（対話）という役割の違い**で分ける。

### 10-1. 無料プラン

「知識を育てる」ために必要な機能一式。**Lumoraの知識化フローそのもの**であり、ここを有料化すると入口が狭まりArcaがそもそも育たなくなるため、恒久的に無料で維持する。

- メモ編集
- マーカー作成
- Arca（マーカー確定）
- `organize-markers`（AIタグ提案）
- `organize-wings`（AIによるWing/章立て提案）
- 横断検索（キーワード/タグ/フィルター）
- タイムライン（Chronicle）閲覧

`organize-markers`/`organize-wings`を無料に含める理由（決定・2026-07-22）：この2つは「知識化」の入口であり、有料化すると「メモだけ貯まる→整理されない→価値を感じにくい→Proへの導線が生まれる前に離脱する」という悪循環になる。Beaconの価値（Arcaが数百個育った状態でAI検索をONにする「知識が一気につながる瞬間」）は、無料側でArcaが十分に育っていることが前提であるため、無料側の充実がPro転換率の土台になる。

### 10-2. Pro（Beacon）

「育った知識と対話する」機能。詳細な機能リストと検索対象の線引き（Arca限定＋Tag併用）は9章「Beacon」参照。

### 10-3. トライアル型を却下した理由（決定・2026-07-22）

期間限定で全機能を無料開放する「N日間トライアル」方式は検討した上で却下した。理由：Lumoraの価値はデータの蓄積量に比例するため、契約直後（Arcaが数個〜十数個）のユーザーがAI検索を使っても「まだ何も覚えていない」という空虚な体験になりやすく、トライアル期間中に価値を実感させるのが構造的に難しい。機能ゲート型（無料で使い続けて自然にArcaが育ち、育った時点でProへ切り替える）の方が、Lumora自身の設計思想（3-3の情報フロー、蓄積型の知識資産）と整合する。却下の経緯は`rejected-decisions.md`に記録。

### 10-4. β運用への適用

β参加者（2〜3人想定）にはentitlementでPro権限を手動付与する。理由：AI検索の品質検証・UX改善・フィードバック収集のためには、無料枠のままではなくPro機能（Beacon）を実際に使ってもらう必要があるため。
