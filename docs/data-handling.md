# data-handling.md — データの取り扱い（開発者向け設計契約）

**この文書は法律文書ではない。開発者が守るべき設計契約である。**

プライバシーポリシー・利用規約・FAQ・セキュリティ説明は、すべてこの文書から生成する。

新しい保存先・新しいAIプロバイダを追加する時は、先にこの文書を更新すること。

作成：2026-07-29。記載内容はすべて同日時点のコードで確認済み（確認方法は各節に記載）。

## 0. 情報フロー（1枚図）

```
  エクスポートファイル（ChatGPT/Claude/Gemini/Perplexity/.md/.jsonl）
        │
        ▼
  ┌─────────────────────────────┐
  │ 端末内（ブラウザ）           │   原本ファイルはここから出ない
  │  パース・正規化              │   Supabase Storageは使用しない
  └──────────┬──────────────────┘
             │  正規化済みテキストのみ
             ▼
  ┌─────────────────────────────┐
  │ Supabase（Postgres）         │   RLSで user_id = auth.uid() のみ
  │  conversations / messages    │
  │  markers / projects / themes │
  └──────────┬──────────────────┘
             │
       ユーザーがマーカーを引く（＝AIに見せる範囲を人間が決める）
             │
             ▼  quoted_text / role_tag / 会話タイトル のみ
  ┌─────────────────────────────┐
  │ Anthropic API（Claude）      │   会話全文は送らない
  └─────────────────────────────┘
```

**AIが読む範囲をユーザー自身が決める**、という構造になっている。これは偶然ではなく、
2026-07-11の情報フロー転換（AIによる自動マーカー発見を廃止し、人間が引いたマーカーだけを
AIの対象にした）の帰結である。最小権限の考え方に相当する。

## 1. どこに保存されるか

| データ | 保存先 | 備考 |
|---|---|---|
| エクスポートの**原本ファイル** | **端末内のみ** | クラウドへ送らない。Supabase Storageは使用していない（`src/`全体で`.storage`の使用0件、2026-07-29確認） |
| 会話・メッセージ（正規化済みテキスト） | Supabase Postgres | `conversations` / `messages` |
| Marker（Arca）とその履歴 | Supabase Postgres | `markers` / `marker_history` |
| Realm / Wing / Tag とその割当 | Supabase Postgres | `projects` / `themes` / `tags` / `marker_tags` / `marker_wings` |
| メモ・色の意味・解放フラグ | Supabase Postgres | `memos` / `marker_color_meanings` / `unlock_flags` |
| AI利用量 | Supabase Postgres | `ai_usage_daily`（件数のみ。本文は含まない） |
| アプリ本体の配信 | Vercel | 静的アセット。ユーザーデータは通らない |

**リージョン**：Supabaseプロジェクトは**東京リージョン**（2026-07-29確認）。
つまり**保管されたデータは日本国内に置かれる**。

**アクセス制御**：全テーブルが`user_id`列を直接持ち、RLSは全テーブル共通で
`user_id = auth.uid()`（`data-model.md` 4章）。他ユーザーの行は取得できない。

### 保管と処理は別である（重要）

**「東京リージョンに保管される」と「データが国外へ出ない」は同じではない。**
保管先が国内でも、2章の外部送信が発生した時点でそのデータは国外へ渡りうる。
プライバシーポリシーでは、この2つを混ぜて書かないこと（「日本国内に保管」とだけ書くと、
AI解析時の越境を隠したことになる）。

| | 場所 | 状態 |
|---|---|---|
| **保管**（Supabase Postgres） | 東京リージョン＝日本国内 | 確認済み |
| **AI解析**（Anthropic API） | 国外（米国）で処理される | 「Knowledge Organize」実行時のみ・送るのはマーカーの抜粋のみ |
| **エラー監視**（Sentry） | **未確認**（Sentryは米国／EUのリージョンを持つ） | 送るのは長さ・ID・エラー情報のみ |
| **配信**（Vercel） | グローバルCDN | ユーザーデータは通らない |

## 2. 何が外部へ送られるか

送信先は3つしかない。**これ以外へ送る実装を追加しない。**

### 2-1. Anthropic API（Claude）

Edge Function `organize-markers` / `organize-wings` から呼ぶ。ユーザーが明示的に
「Knowledge Organize」を実行した時のみ発火する（**自動実行しない**）。

| 送るもの | 送らないもの |
|---|---|
| `markers.quoted_text`（マーカーを引いた抜粋） | **会話全文**（`messages.content`） |
| `markers.role_tag` | メールアドレス・アカウント情報 |
| 所属会話のタイトル | 原本ファイル |
| 既存のTag名（`organize-wings`のみ） | 他ユーザーのデータ（RLSで到達不能） |

確認箇所：[`organize-markers/index.ts:152`](../supabase/functions/organize-markers/index.ts)、
[`organize-wings/index.ts:170`](../supabase/functions/organize-wings/index.ts)

**学習利用について**：Anthropicの商用APIは、既定で顧客の入力・出力をモデルの学習に
使用しない。**ただし「そう聞いた」で済ませず、規約の該当箇所を確認し、確認日とともに
下記に記録すること**（千代田区の事例が示すとおり、契約を確認した事実こそが信頼の根拠になる）。

- 確認日：**未実施**
- 参照した規約の箇所：**未記入**

### 2-2. Sentry（エラー監視）

| 送るもの | 送らないもの |
|---|---|
| エラーメッセージ・スタックトレース | メールアドレス（`beforeSend`で削除） |
| `user.id`（uuid）のみ | 会話本文・マーカー本文 |
| 現在の画面パス（`route`タグ） | コンソール出力（Console統合を除去、breadcrumbも破棄） |
| 明示的に渡した`extra`（例：`quotedTextLength`＝**長さのみ**） | キー名が機微と判定された`extra`（`beforeSend`でスクラブ） |

確認箇所：[`src/lib/sentry.ts`](../src/lib/sentry.ts)。`sendDefaultPii: false`、
`tracesSampleRate: 0`。

**規律**：Sentryへ本文そのものを渡さない。長さ・件数・IDに留める。既存の
`reportPositionMismatch`は`quotedTextLength`（長さ）だけを送っており、これが基準例。

### 2-3. Vercel（ホスティング）

アプリのHTML/JS/CSSを配信する。ユーザーデータはVercelを経由しない
（クライアントからSupabaseへ直接通信する）。アクセスログにIPアドレス等が残る点は
一般的なホスティングと同じ。

## 3. 削除の仕様

**ここはPrinciple 3（知識は破壊しない）と混同されやすいので、区別を明確にする。**

Principle 3が禁じているのは**システムによる破壊**であって、**ユーザー自身の削除**ではない。
詳細は`PRINCIPLES.md` Principle 3。

| 操作 | 現在の挙動 | 物理削除 |
|---|---|---|
| マーカーを外す | `status: 'rejected'`（論理削除）。履歴とともに残る | しない |
| Wing/Tagを外す | 中間テーブルの`status`変更 | しない |
| 会話を保留する | `held_at`をセット。一覧から除外 | しない |
| 保留一覧から「完全に削除」 | **物理削除**（2段階の明示操作が必要） | **する** |
| **アカウント削除** | **未実装** | — |

### ギャップ（ローンチ前に解消すること）

- **アカウント削除の導線が存在しない**（`src/`全体でgrep 0件、2026-07-29確認）。
  知識を預かるプロダクトにとって「いつでも離れられる」ことは信頼の一部であり、
  削除手段が無いこと自体が「閉じ込められる」印象を与える。**ローンチのブロッカー**
- 削除時にAnthropic/Sentry側へ送信済みのデータをどう扱うかの記述が無い
  （各サービスの保持ポリシーに従う旨を書く必要がある）

## 4. 保持期間

**未定義。** 現時点でLumoraは、ユーザーが明示的に削除しない限りデータを保持し続ける。

ローンチ前に次を決めること：

- アカウント削除後の完全消去までの猶予（即時か、一定期間の復旧可能期間を置くか）
- Sentryのイベント保持期間（Sentry側の設定に依存）およびSentryプロジェクトのリージョン
- ログの保持期間（Vercel / Supabase）

## 5. この文書を更新すべきタイミング

以下のいずれかを行う時は、**実装より先に**この文書を更新する。

- 新しい外部サービスへデータを送る（AIプロバイダの追加を含む）
- 既存の外部送信の内容を増やす（例：会話全文をAIへ送る設計への変更）
- 新しい保存先を追加する（Supabase Storageの利用開始を含む）
- 削除・保持の挙動を変える
- リージョンを変更する

`CLAUDE.md`の「外部送信が発生する箇所は、どのデータがどこに送られるかを明示する」という
ルールの、具体的な適用先がこの文書である。
