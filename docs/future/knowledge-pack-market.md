## 1. 何を売るのか

一般的なAIボット販売は「キャラクター設定＋プロンプト＋会話スタイル」であり、模倣に近い。
Lumora型はそこではない。

| | 売っているもの |
|---|---|
| ❌ | この人**っぽく話す**AI |
| ⭕ | この人が長年蓄積した**判断材料・観点・知識構造** |

前者は人格の再現であり、`EVIDENCE-OS.md` 12章の非目標1つ目
「**AI人格を作ることを目的としない**」に抵触する。後者は知的資産であり、抵触しない。

**非目標が、危ない側の設計を最初から排除している。** この構想が成立しうるのは、
その線引きが先にあるからである。

例：「有名マーケターAI」は危険（その人ならこう言うはず、という人格再現）。
「EC改善Realm」は成立する（商品ページを見る順番／CVRで見る指標／改善案を出す前の
確認事項／過去事例／判断基準）。

## 2. なぜ「名もなき達人」なのか

有名人よりも、町工場の職人・古書店主・美容師のような**個人の中に閉じた暗黙知**の方が
Lumoraと噛み合う。理由はLumoraの語彙で説明できる。

**有名人の意見は既に公開されており、根拠へ戻る価値が薄い。** 一方、40年の金属加工職人の
判断は本人の頭の外にどこにも無いため、**根拠を保存する意味が最大になる。**

職人の価値は「答え」ではなく「**何を見るか**」にある。

```
一般人：表紙が綺麗だから価値がありそう
古書店主：初版か／装丁家は誰か／奥付の出版社変遷／著者の時代的位置づけ／市場在庫量
```

この「見るポイント」がMarkerとして部品化できる。

## 3. 構造的な問題：売ると根が切れる

**売られたRealmは「根拠へ戻れる」を満たせない。** これがこの構想の最大の障害である。

Arcaは`quoted_text`（抜粋）と`conversation_id`/`message_id`を持ち、そこから元の会話へ
戻れる。これが`PRINCIPLES.md` Principle 4 と憲法5の実体である。Realmを売ると、この鎖が切れる。

| 案 | 何が起きるか |
|---|---|
| 元の会話も一緒に売る | 職人へのインタビューには取引先名が、美容師の記録には客の情報が入る。**利用規約 第7条3項（第三者の個人情報）に真正面から当たる** |
| Arcaだけ売る | 買い手は**根拠を辿れない主張の束**を受け取る。憲法5が成立せず、Beacon・Compassも検証できない |

**どちらも既存の原則を壊す。追加機能では解けない。**

### 第3の道：根の定義を変える

```
現在   ： 根 ＝ 一次情報（元の会話）
販売時 ： 根 ＝ 出所が明示された「判断の記録」そのもの
```

売り物を会話ではなく「**観察 → 判断 → 理由 → 結果**」の連鎖とし、**それ自体が一次情報として
自立している**という設計にする。

```
観察：髪が細い／カラー履歴あり
判断：薬剤パワーを下げる
理由：過去に同条件で切れ毛が発生した
結果：ダメージ回避
```

**Decision Layerは機能追加ではなく、憲法5を販売可能にするための唯一の道である。**
順序が逆であることに注意すること——Decision Layerがあるから売れるのではなく、
**売るなら他に選択肢が無い。**

## 4. Decision Layerの種は既にある

```sql
create type marker_role_tag as enum ('idea', 'hypothesis', 'decision', 'strategy', 'learning');
```

`decision`は**2026-07-10の最初のマイグレーションから存在している**。ただし現在、
**この列に書き込むコードは1行も無い**（`confirmPendingMarker`の`insertPayload`に
`role_tag`が含まれていない）。読み出しはするが、誰も書いていない列である。

「判断を一級の対象として扱う」という発想は最初から入っていて、実装だけが追いついていない。
**Decision Layerは新概念というより、放置された種に近い。**

着手時は、新しいテーブルを作る前に**この列を活かせないか**から検討すること
（`EVIDENCE-OS.md` 12章 非目標3つ目「Evidenceという新しいデータモデルを追加しない」）。

## 5. 品質保証がなぜ難所になるか

市場化すると必ず問題が出る——間違った知識を売る人、根拠のない専門家パック、偏った判断基準、
古い情報の放置。

普通のAIサービスなら「便利そう」で売れてしまう。Lumoraなら、**Realm自体に評価軸を持てる。**

```
Realm
 ├ Evidence数
 ├ Evidence種類
 ├ 更新日
 ├ 作成者
 ├ 検証履歴
 ├ 利用者評価
 └ 信頼レベル
```

**「誰が言っているか」ではなく「何を根拠に形成された知識か」を見せる。** これはEvidence First
と直結する。したがって、もしストアを作るなら**アプリストア型（人気ランキング）ではなく、
学術データベースや職人市場に近い設計**になる。

## 6. 着手時に必ず解くこと（未解決の4点）

**これらを解かずに実装へ降ろしてはならない。**

### 6-1. 根の定義（最重要）

3章のとおり。「一次情報＝元の会話」のまま販売すると、privacy か 憲法5 のどちらかが壊れる。
**根の定義を2種類持つのか、Decision Layerを新しい一次情報とみなすのかを決めること。**
決着するまで、他の3点は設計できない。

### 6-2. Decision Layer と `role_tag` の関係

4章のとおり。既存のenumを活かすのか、別の構造にするのか。
`data-model.md`「RealmとViewの責務分離」に照らし、**まずViewで足りないか**を検討すること。

### 6-3. Stable Identity（`EVIDENCE-OS.md` 11-2 A-2）

現在**未確定**として置いてある条項。Realmを配布すると、これを未確定のままにできない。

同じRealmが100人にコピーされ、それぞれが編集し、元が更新される。
**「これは同じ知識か」を判定できなければ、更新履歴も信頼スコアも成立しない。**

**販売を検討に入れた時点で、A-2は「いつか決める」から「先に決める」に変わる。**

参考：現状、Markerの同一性は保たれている（色・範囲・Wing・Realm・`edited_text`の変更は
すべてUPDATE）が、Chronicleの同一性は保証されていない（再インポートで別uuidの行が増える。
`importService.ts`に重複排除が無い）。

### 6-4. 買ったRealmは検索対象か

`search-spec.md` 2-1 は検索対象を「**ユーザー自身が作成またはインポートした一次情報**」と
定義している。買ったRealmは**インポートされるが、ユーザーが作ったものではない**。

同 1章の「**まだ知識化していない会話を発掘する場所**」という定義とも噛み合わない。
買ったRealmは既に整理済みだからである。**検索対象に入れるか、別の探索手段を用意するかを
決めること。**

## 7. 現在のLumoraとの距離

| | 状態 |
|---|---|
| 情報を保存する／断片化する／根拠へ戻れる／再構成する／Realm化する | **実装済み。かなり近い** |
| 専門家Realmとして参照させる | Beacon（Phase2）の延長で可能 |
| 暗黙知の抽出（Interview Mode等） | **追加設計が必要** |
| 判断の連鎖（Decision Layer） | **種のみ存在**（4章） |
| 配布・流通・信頼スコア | **未着手。6章を解くのが先** |

## 8. この構想の位置づけ

```
最初   ：自分のワーキングメモリを補う
  ↓
発展   ：自分の思考資産を保存する
  ↓
さらに ：人類の中に眠る暗黙知を持ち運べる形にする
```

この方向へ進む場合、Lumoraの比較対象はNotionやEvernoteではなくなり、
「知識を所有・継承・流通するためのインフラ」という別のカテゴリーに入る。

ただし**それはPhase3以降の話であり、Phase1のスコープを1ミリも変えない。**
