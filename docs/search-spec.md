# search-spec.md — 横断検索仕様（Phase1確定・2026-07-13）

横断検索（S8）はLumoraの中核仕様であり、UIの一部ではない。**検索の目的・原則・UX・設計思想**をこのファイルに集約する。画面遷移・UI配置は`ux-flow-and-screens.md`、検索の目的の背景にあるプロダクト哲学は`VISION.md`（3-3）を参照。

**このファイルの境界（重要）**：本ファイルは「検索の憲法」であり、`ILIKE`／`pg_trgm`／全文検索エンジン／ベクトル検索といった**具体的なアルゴリズム・SQL実装は対象外**とする。実装が何を使おうと（将来pg_trgmから全文検索エンジンへ、あるいはベクトル検索へ移行しようと）、ここに書かれた原則は変わらない、という状態を保つのがこのファイルの役割。アルゴリズムの詳細は、実装する側（migration・RPC・Edge Functionのコード内コメント）に書く。

---

## 0. 設計原則（最上位・これに反する変更はしない）

- **検索は整理済み知識を読む機能ではない。未整理の一次情報を発掘する機能である。**
- **検索語を追加するほど検索結果は単調に絞られることを基本原則とする。**
- **検索条件はAIが自動変更しない。検索条件を変更するかどうかは、必ずユーザーが選択する。**
  - **システムは検索意図を推測して条件を書き換えない。** これはAIだけの話ではなく、検索UI自身にも適用される。自動スペル修正・自動OR・自動関連検索・自動ランキングは、いずれも「ユーザーが入力した条件」を黙って別の条件に置き換える行為であり、行わない（個別の帰結は3-4・3-5・4章）
- **検索結果は決定的（Deterministic）でなければならない。同じデータ・同じ検索条件・同じ並び順を指定した場合、常に同じ結果・同じ順序を返す。**

以降の全ての仕様は、この4原則から逆算して決まっている。新しい検索機能を検討する時は、まずこの4原則に反しないかを確認すること。検索**対象**の判断基準（何を検索できるようにするか）は2章の「一次情報」原則を参照。

4つ目が原則として要る理由：Lumoraは記憶を扱う道具であり、**同じ検索をすれば同じ場所に戻ってこられる**ことが信頼性そのものになる。「昨日ここで見つけた」が今日再現できなければ、発掘という行為自体が成り立たない。一見当たり前に見えるが、検索は放っておくと決定性を失う（インデックス更新のタイミングで順位が揺れる、関連度の微調整で昨日と結果が変わる、あいまい一致の閾値変更でヒット件数が変わる）。守り方の具体は3-6を参照。

**決定性は実装ではなく契約である。検索アルゴリズムやデータベースを変更しても、この原則を破ってはならない。** PostgreSQL → Meilisearch → Lucene → 独自検索 → Embedding併用、どこへ移行しても実装は自由だが、ユーザーとの約束は変わらない。したがってこの一文は、検索基盤を差し替える際の**移行の合否判定**としてそのまま使える——新しい基盤が速くても賢くても、決定性を返せないなら採用しない。

1つ目を否定形で書いているのは、それだけでRealm検索・Wing検索・Tag検索・AI要約検索・AIによる直接回答をまとめて排除できるため（**整理済み**の構造を読む機能はすべてこれに反する）。

## 1. 検索の役割（Knowledge OSらしさの核）

普通の検索エンジンは「見つけること」が目的で、結果はそこで完結する。Lumoraの横断検索はそうではない。

> **横断検索は「答えを見つけて終わる場所」ではなく、「まだ知識化していない会話からArcaを発掘するための入り口」である。**

検索結果画面は「答えを読む場所」ではなく「まだ整理されていないChronicleを発掘し、本文を選択してマーカー（Arca）を作る場所」として設計する。将来、検索結果に要約やAIによる直接回答を載せるような機能案が出た場合、それは「答えを読んで終わる」体験を作ってしまわないかをこの一文に照らして判断すること。

**検索が対象とするのは「まだ整理されていない知識」**である。Realm・Wing・Tagは整理**後**の構造であり、これらを検索対象・検索結果に混ぜると、既に整理済みの知識が結果に多く現れ、発掘体験にとってノイズになる（2026-07-13、実装検討時の議論で確定）。検索対象の具体的な判断基準（「一次情報」原則）は2章を参照。

## 2. 検索対象

### 2-1. 検索対象を決める基準：「一次情報」原則

**検索対象は「ユーザー自身が作成またはインポートした一次情報」を基本とする。**

- **一次情報に含まれるもの**：ユーザーが自分の手で書いた言葉（メモ、マーカー説明）、およびユーザーがLumoraに取り込んだ元データそのもの（AIとの会話本文。将来的には画像OCR・PDF・音声・動画・Web記事から抽出したテキストも含まれる）
- **一次情報に含まれないもの**：Realm名・Wing名・Tagのような、一次情報に対して後から付与された組織化ラベル・構造（1章で述べた「整理後の構造」と同義。恒久的に対象外）

この基準を採用する理由は、**検索対象を固定リストではなく原則で定義しておくこと**にある。将来インポート対応が画像OCR・PDF・音声・動画・Web記事等に広がっても、「それが一次情報かどうか」だけを判定すればよく、検索対象の定義そのもの（この原則）を都度書き換える必要がない。

### 2-2. 現在・将来の対象一覧（一次情報原則からの導出）

| 分類 | 具体例 | フェーズ |
|---|---|---|
| インポートされた会話本文 | ChatGPT/Claude/Gemini/Perplexity（`conversations.title`, `messages.content`） | Phase1 |
| インポートされた汎用文書 | Markdown/テキストファイル（`source: "document"`、2026-07-14追加。`import-spec.md`5-1参照） | Phase1 |
| インポートされた開発セッション記録 | Claude Code CLIの`.jsonl`（`source: "claude_code"`、2026-07-21追加。`import-spec.md`5-2参照） | Phase1 |
| ユーザーが書いた注釈 | メモ（`memos.body`） | Phase2以降 |
| ユーザーが編集した知識 | マーカー説明（`markers.edited_text ?? markers.quoted_text`） | Phase2以降 |

**メモ・マーカー説明について（補足・2026-07-28）**：この2つは元データそのものではなく、ユーザーが後から書いた・編集したテキストであるため、「一次情報ではないのでは？」と読まれうる。**マーカー説明はユーザー自身が作成した知識であり、一次情報を補足・編集したユーザー生成情報として検索対象に含める。** メモも同じ扱い。

ここで分けている線は「加工されているかどうか」ではなく、**人間が自分で書いたか／後から付与された組織化ラベルか**である。Realm名・Wing名・Tagが恒久的に対象外なのは加工済みだからではなく、一次情報に対する分類ラベル（しかもWing/TagはAIが提案した構造）だからである。

**未決事項**：マーカー説明の検索対象は表では`edited_text ?? quoted_text`としているが、この式だとユーザーが編集した瞬間に**原文（`quoted_text`）が検索から消える**。`quoted_text`は生成時に固定される不変の一次情報であり（`data-model.md` 0章）、`PRINCIPLES.md` Principle 4「根拠へ戻れる」の対象そのものなので、編集によって検索から消えるのは原則と緊張する。Phase2で実装する際に、両方を検索対象にするか（`edited_text`と`quoted_text`の両方に一致判定をかける）を改めて判断すること。

**将来的な拡張の考え方**：画像OCR・PDF・音声（文字起こし）・動画（文字起こし）・Web記事等、Lumoraが将来対応するインポート形式が増えても、それが「ユーザー自身が作成またはインポートした一次情報」であれば、この原則（2-1）にそのまま当てはまる。個別の対応時期は`import-spec.md`の対象範囲拡張とセットで、Phase2以降の中で改めて検討する（VISION.mdの他バックログ項目と同様、独立した新しいフェーズ番号は設けない）。

### 2-3. 対象外（一次情報ではないため、恒久的に対象外）

Realm名・Wing名・Tag（1章参照）。

## 3. マッチングロジック（デフォルト）

> **検索は「一致判定」と「表示順」を明確に分離する。一致するかどうかは検索条件のみで決まり、表示順はユーザーが選択する並び替えによってのみ決定される。システムは関連度推定によって検索結果の順序を変更しない。**

一般的な検索エンジンは「一致 → 関連度 → 順位」が一体になっている。Lumoraは「一致 → ユーザーが並び替え」であり、ここが最も思想の違う部分にあたる。関連度スコアで並べ替える実装提案が将来出てきた場合、この一文だけで仕様レベルで退けられる。

**本章の記述水準（RFC 2119に準拠）**：**MUST**＝必ずそうする（変更には本ファイルの改訂が必要）。**SHOULD**＝原則そうするが、実装上の理由があれば逸脱を記録した上で可。**MAY**＝実装してよいが必須ではない。

### 3-1. 検索文法（Search Grammar）

将来の拡張に備え、トークン化ではなく**文法**として定義する。演算子を後から足す時に、この表へ行を追加するだけで済む形にしておく。

| 文法 | 意味 | 段階 | 水準 |
|---|---|---|---|
| `古着 技術` | スペース区切りでトークンに分割し、AND | Phase1 | **MUST** |
| `"技術 スタック"` | 1つのフレーズとして扱う（語順・隣接を保持） | Phase1 | **MUST** |
| `-Shopify` | NOT（除外） | Phase2以降 | MAY |
| `title:古着` | タイトルに限定 | Phase2以降 | MAY |
| `source:claude` | 取り込み元で絞る | Phase2以降 | MAY |
| `before:2026-01` | 日付で絞る | Phase2以降 | MAY |

フレーズはオプトインである（**MUST**）。現行実装のように入力全体を常にフレーズとして扱うことはしない。

**演算子を追加する時の必須条件（MUST）**：`-` や `:` は日本語の本文にも普通に現れる（「-1」「メモ:」「17:30」等）。演算子を導入する際は、**それを演算子ではなくただの文字として検索する手段を同時に定義する**こと（`"` で囲めばリテラルになる等）。これを後回しにすると、ある日から特定の文字列が検索できなくなる。

**フィルタと検索対象は別である（MUST）**：`source:` のような接頭辞は**検索対象を増やすものではなく、結果を絞るもの**である。したがって `realm:` `wing:` `tag:` は**導入しない**。これらは整理**後**の構造であり、検索体験に持ち込まない（1章・2-3）。「フィルタなら対象外原則に触れないのでは」という理屈は成立しない——絞り込みであっても、ユーザーは整理済みの構造を頼りに検索することになるためである。

### 3-2. Chronicleを1つの検索単位とする

**会話（Chronicle）全体を1つの検索ドキュメントとして扱う（MUST）。** 検索エンジンでいうDocument Unitにあたる単位を、Lumoraでは会話に置く。

```
Conversation（＝1検索単位）
├ タイトル
├ Message 1
├ Message 2
└ Message 3
```

各トークンは、この単位の**どこか**に部分一致すればよい。1つのメッセージの中に全トークンが揃っている必要はない。

> 例：メッセージAに「古着」、メッセージBに「技術スタック」が存在すれば、その会話はヒット対象。

全トークンが（会話内のどこかで）満たされて初めてヒットする。1つでも満たされないトークンがあれば対象外（厳密AND）。

```
検索入力  「古着 技術」
   ↓
Tokenize   ["古着", "技術"]
   ↓
Chronicle単位でAND判定
   ┌─────────────────────────┐
   │ Conversation            │
   │  タイトル    ← "古着"    │
   │  Message 1              │
   │  Message 2  ← "技術"    │
   │  Message 3              │
   └─────────────────────────┘
   ↓
全トークンが成立
   ↓
ヒット（この会話が1件として返る）
   ↓
表示順はユーザーの並び替えのみで決まる（一致判定は順序に関与しない）
```

### 3-3. 結果の単位

- **検索結果の最小単位はConversation（Chronicle）である（MUST）。**
- **Messageは検索結果ではなく、検索結果から到達する着地点である（MUST）。**
- **検索結果はConversationを返し、その中に複数の一致箇所を保持してよい（MAY）。**

**なぜMessageを結果の単位にできないか**：3-2でANDを会話スコープに広げたため、個々のMessageは単体でクエリを満たすとは限らない。「古着 技術」が別々のメッセージに分かれて成立している場合、Message単位の行はいずれも**部分一致**になり、4章（部分一致を最初から見せない）に反する。結果の単位は、**クエリが成立する単位より小さくできない**。3-2を決めた時点でこの帰結は確定していた。

普通の検索エンジンは一致単位と結果単位が揃っているためこの問題が起きない。Lumoraは意図的にANDを会話スコープへ広げたので、結果単位を下ろす選択肢が無い。

**着地点（MUST）**：Markerはメッセージ単位・オフセット単位の行為である。検索結果が会話IDしか渡さないと、発見（検索）と作成（Marker）の間で位置情報が切れ、ユーザーは会話の先頭から目視で探し直すことになる。一致箇所は`message_id`と本文中の位置を伴って返し、そこへ着地できること。

**一致件数（match_count・SHOULD）**：会話ごとの一致件数を返す。「一度触れただけ」なのか「何十回も議論している」のかが分かる。**これはランキングではなく情報である** — 一致判定にも既定の順序にも影響しない（3章冒頭）。

ただし2点、制約が付く。

- **システムがmatch_countを使って自動的に順位を決めることは禁止（MUST NOT）。** ユーザーが選べる並び替え軸として提供するのは可（表示順はユーザーの選択のみで決まる、という原則の範囲内）
- **match_countの数え方は、ハイライト表示の数え方と一致していなければならない（MUST）。** 重なり合う出現の扱いで両者がずれると、「8件と書いてあるのに7箇所しか光らない」が起きる。日本語では実際に起こる（本文`"あああ"`の中の`"ああ"`は2箇所。`replace()`の長さ差で数えると1回になる。詳細は`CHANGELOG.md` 2026-07-27）

**採掘状態の示し方（SHOULD）**：1章のとおり検索の目的は「まだ知識化していない会話を発掘する」ことなので、その会話から既にArcaを作ったかどうかは、この目的に直接効く情報である。ただし**マーカー件数を前面に出さない**。件数を出すと「整理済み度」が主役になり、未整理を掘るという目的から意識がずれる。**採掘したかどうかの状態**（未採掘／一部採掘済み）を示し、件数が要る場合は展開後に出す。

なおこれは2-3（Realm/Wing/Tagは恒久的に対象外）と衝突しない。採掘状態が参照しているのは**Arcaが存在するかどうか**であって、後から付与された組織化ラベルではない。検索自身の目的に属する情報である。

具体的な文言・記号・配置は`ux-flow-and-screens.md`（S8）の領域とし、本ファイルでは「件数ではなく状態を示す」という原則までを規定する。

### 3-4. 一致の種類

部分一致（大文字小文字を無視した連続文字列一致）のみをデフォルトとする（**MUST**）。あいまい一致（表記ゆれ・タイプミス吸収）はデフォルトでは行わない（5章のフォールバック時のみ使用）。フレーズ（`"..."`）は**語順と隣接関係を保持する**（**MUST**）——`"技術 スタック"` は「技術」と「スタック」がこの順で連続している箇所にのみ一致し、離れて出現する場合は一致しない。どの技術（`ILIKE`／トライグラム／全文検索エンジン等）でこれを実現するかは実装側の判断であり、本ファイルが規定するのは「デフォルトは厳密な部分一致であり、あいまい一致ではない」という挙動のみ。

### 3-5. 並び順

検索結果の並び替え（新しい順／古い順／長い順／短い順）はユーザーが選ぶ既存UIのまま変更しない（**MUST**）。本仕様では「関連度スコアによる自動ランキング」は採用しない（**MUST NOT**）。3章冒頭の分離原則の直接の帰結であり、0章の4原則とも同じ考え方（順序もユーザーが選ぶ形を維持し、システム側が独自の関連度判断で並びを決めることはしない）。

### 3-6. 決定性（Determinism）

0章の4つ目の原則を、実装が守れる形に落としたもの。

**同じデータ・同じ検索条件・同じ並び順に対して、常に同じ結果集合・同じ順序を返す（MUST）。**

決定性は放っておくと失われる。以下は「守るつもりでも破れる」具体的な穴であり、実装時に必ず塞ぐこと。

**1. ソートキーが同値の時、順序は保証されない（MUST：一意なタイブレーカーを付ける）**

「新しい順」だけでは、`created_at`が同一の会話どうしの順序が決まらない。SQLは同値行の順序を保証せず、**同じクエリを2回投げるだけで入れ替わりうる**。ページングを入れると、この揺れは「2ページ目に同じ会話がまた出る」「1件が どのページにも出ない」という形で表面化する。

並び替えのキーの最後に、必ず一意な列（`id`等）を付けること。

**2. `conversations.created_at`はNULLを取りうる（MUST：NULLの位置を明示する）**

`data-model.md`のとおり`created_at`は`datetime | null`である（元サービス側の作成日時が取れない場合がある）。**これは仮定の話ではなく、既に成立している条件**。NULLの並び位置（`NULLS FIRST` / `NULLS LAST`）を明示しなければ、DBの既定に依存した順序になる。明示すること。

**3. あいまい一致の閾値を変えることは仕様変更である（MUST：記録を伴う）**

フォールバック（5章）で使う類似度の閾値を調整すると、**同じ検索条件でヒット件数が変わる**。これはチューニングではなく、ユーザーから見える挙動の変更である。変更する時は理由と日付を記録すること（`CHANGELOG.md`）。黙って調整しない。

**4. 「同じデータ」の範囲（参考）**

会話やメッセージが増減すれば結果が変わるのは当然であり、決定性の違反ではない。この原則が禁じているのは、**データが変わっていないのに結果や順序が変わること**である。

## 4. デフォルトで表示しないもの

- OR検索結果（一部のトークンだけ一致したもの）は、AND結果と混ぜて最初から表示しない
- 部分一致グループ・関連度ランキングのような「段階的な緩和済み結果」も、フォールバックが発動する前は表示しない

これは1章の思想（「答えを読んで終わる場所ではない」）とも関係する：曖昧な結果を最初から大量に見せることは、発掘という行為の質を下げる。

## 5. フォールバック（0件の時のみ、ユーザー確認必須）

**検索条件はAIが自動変更しない。検索条件を変更するかどうかは、必ずユーザーが選択する。**

厳密AND検索の結果が0件になった場合のみ、次を行う。

1. 結果0件を検知したら、ユーザーに対して**「検索条件を緩めますか？」**と明示的に提示する（バナー・インラインの確認UI等、実装時に画面設計）
2. ユーザーが選択した場合にのみ、緩和した条件で再検索する

**「緩める」の具体的な内容（どのトークンを外すか、AND→ORに切り替えるか、あいまい一致にどう切り替えるか等）は実装時に判断する未決事項**とし、本ファイルでは規定しない。実装アルゴリズムの選定・詳細は、実装するmigration・RPC・Edge Functionのコード内コメントに書くこと。

本ファイルが規定するのは挙動レベルの原則のみ：**フォールバック結果は「厳密一致の結果ではない」ことをUI上で明示する**（例：「〇〇を含む結果はありませんでした。△△の結果を表示しています」「もしかして」等の文言）。厳密一致とフォールバック結果を混同させないことは、0章の4原則（AIが勝手に緩めない）を守るための必須条件であり、緩和後もその出自を隠さないことまでが原則の範囲に含まれる。

## 6. Beaconとの役割分担（Phase2以降）

| | 横断検索（本仕様） | Beacon（AIによる関連発見・Phase2バックログ） |
|---|---|---|
| 目的 | 「思い出せる言葉がある」時に、まだ知識化していない会話を発掘する | 「言葉にできないが関連はある」ものを、意味的な近さで発見する |
| 検索方式 | トークンの部分一致・厳密AND（本仕様） | 埋め込み（embedding）による意味検索 |
| 対象データ | ユーザー自身が作成・インポートした一次情報（2章参照。未整理含む） | Arca（confirmedマーカー、既に厳選された知識） |
| コスト | ほぼゼロ（DBクエリのみ） | AI API呼び出しが発生する |
| 説明可能性 | 高い（どの単語がどこに一致したか明示できる） | 低い（関連性の理由が直感的でない場合がある） |
| 発動 | 常時・即時（検索窓に入力すれば動く） | ユーザーの明示的な操作、または将来的な追加導線（未設計） |

横断検索は「発掘の土台」であり、Beaconはその上に育つ機能という位置づけ（VISION.md 9章に既にある記述「Arcaが厳選済みデータになったのでBeaconの精度が上がる」という論理は、本仕様がしっかり機能することが前提になる）。横断検索とBeaconは競合するものではなく、前者が「言葉を覚えている」場面を、後者が「言葉にできない関連」を、それぞれ別々に担う。
