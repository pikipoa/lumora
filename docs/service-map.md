# service-map.md — サービス台帳（依存関係・障害影響・離脱可能性）

> **この文書と`infra.md`の違い**：`infra.md`は「このサービスを採用するか」の判断記録。
> 本書は「採用したサービスが何を持ち、何に依存し、無くなったら何が起きるか」を横断的に
> 一覧化する台帳。個別の採否理由は`infra.md`、横断的な地図は本書、と役割を分ける。
>
> **この文書は継続的な確認を前提とする。** 埋まっていない列は「まだ確認していない」ことを
> 意味し、推測で埋めない（`data-handling.md`と同じ運用ルール）。各行の最終確認日を過ぎたら
> 疑うこと。

作成：2026-08-01。

## 0. 用語の訂正（記録として残す）

台帳を作る過程で、社内の会話で「外部AI：OpenAI / Anthropic / Google Gemini」という
書き方が出た。**これは誤り。訂正する。**

| 誤解 | 実態 |
|---|---|
| OpenAI・Gemini・AnthropicがLumoraの「外部AI」である | **LumoraがAPIとして呼び、処理を委託しているのはAnthropicのみ**（`docs/data-handling.md`確認済み） |
| — | OpenAI（ChatGPT）・Gemini・Perplexity・Claudeは**インポート元**——ユーザーが各社サービス上で行った会話をエクスポートし、Lumoraへ取り込む対象。Lumoraがこれらのサービスへ何かを送信することはない |

**「AI処理を委託する外部事業者」と「ユーザーが会話を取り込む元サービス」は別の分類である。**
本書の1章はこの2つを別カテゴリとして扱う。

## 4. 障害マトリクス（2章から抽出・要点のみ）

| 障害 | 影響 | 影響を受けないもの |
|---|---|---|
| GitHub停止 | 新規開発・自動デプロイが止まる | 稼働中のVercel/Supabaseは無事 |
| Vercel停止 | Web版へアクセスできない | データの保存・削除機能自体は無事 |
| Supabase停止 | **ログイン・保存・検索・整理が全て止まる** | なし。単一障害点 |
| Anthropic停止 | **AI整理機能のみ停止** | 閲覧・検索・Marker作成・保存は継続する |
| Sentry停止 | エラーの可視性が低下 | アプリの動作自体に影響なし |

**設計判断として言えること**：AIが止まっても、記憶の閲覧と保存は可能である
（Anthropicへの依存はSupabaseへの依存より弱い、という設計になっている）。
一方、**Supabaseは唯一の単一障害点であり、代替候補の評価（PostgreSQL自体は移行しやすいが
RLS/Auth/Edge Functionsの書き換えが要る）は本書2章のとおり未着手**。

## 6. この文書が示す設計原則（現状で言えること）

- **GitHubが止まっても、利用者の記憶は消えない**（Supabaseが独立して稼働するため）
- **Vercelが止まっても、データの正本は残る**（正本はSupabase、Vercelは配信のみ）
- **AIが止まっても、MarkerとRealmは読める**（Anthropicへの依存はAI整理機能に閉じている）
- **Supabaseから離れる必要が生じた場合の持ち出し手段は、現時点で無い**
  （`pg_dump`は未検証、Realm Exportは未実装）——**これが本書で最も重い未整備事項**
- 運営者側の単一障害点（契約者アカウント）の整理も未着手

「運営者がいなくなっても利用者自身が記憶を回収できる」状態には、**5章の3・7が
解決するまで到達していない。** 理念を実行可能にする作業として記録する。
