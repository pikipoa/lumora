# settings-ia.md — 歯車アイコン設定画面の情報設計（構想、2026-07-13）

VISION.md「1-1. Core Vision」から生まれた、設定画面全体の情報構造。**この文書は設計のみを確定するもので、実装順序・着手時期は別途判断する**（着手する節ごとにCLAUDE.md 2-6のUIレビューを経る）。

---

## 0. Context（なぜこの画面が必要か）

- 直接のきっかけ：マーカーの色（🩷💚💛💙❤️）にユーザー自身が意味を登録できるようにしたい、という要望（VISION.md 1-1参照）。単に「登録フォームをどこかに置く」のではなく、それが属する「設定」という概念の全体像を先に決めておきたい、というピキさんの判断
- Lumoraにとっての「設定」は、一般的なアプリの環境設定（Profile）だけでなく、**知識の意味づけルールそのもの（Knowledge）**を含む点が特殊。ここがVISION.mdの「AIとの共通言語」構想と直結する

---

## 1. エントリーポイント

**ホーム画面右上に歯車アイコン**（他の画面には出さない）。

理由：DESIGN.md「Remove Before Add」の原則に従い、常設ナビゲーションを増やさない。現状ホーム画面には既に「ワードマーク長押し＝ログアウト」という隠れ導線があるが、設定は今後複数の項目を持つため、専用の入口を1箇所だけ設ける。歯車から先（`/settings`配下）はHomeLinkで通常通りホームへ戻れる。

## 2. 全体構成

`/settings` は4セクションのタブ/リスト構成。

```
⚙ 設定
├─ ① Profile（自分）
├─ ② Knowledge（知識）※Lumoraの核
├─ ③ Integrations（接続）

```

各セクションの成熟度（＝今すぐ作れるか、土台が要るか）を明示しながら以下に記す。

## 3. ① Profile（自分）

一般的なアカウント設定。Lumora固有の思想は薄い。

| 項目 | 現状 | 判断 |
|---|---|---|
| アカウント | Supabase Auth実装済み。ログアウトはワードマーク長押しで既存 | メールアドレス表示程度の軽い画面。ログアウト導線をここに統合するか、既存の長押しと併存させるかは実装時に判断 |
| サブスク | 課金基盤ゼロ。料金モデル（無料＝知識を育てる／Pro＝Beacon）は確定済み（決定・2026-07-22、`VISION.md`10章） | ローンチに向けてentitlement・課金導線の実装が必要。画面自体は「現在のプラン表示＋Proへのリンク」程度の軽いものでよい |
| テーマ（Appearance） | `useColorScheme`でOS追従の自動切替は実装済み | ライト/ダーク/自動の手動切替トグルを追加するだけなので比較的軽い |
| 言語 | `src/i18n/ja.ts`辞書基盤は実装済みだが`en.ts`が無く、ランタイム切替もない | コストの主体は英語データの用意（翻訳）。切替UI自体は軽い |
| 通知 | `expo-notifications`基盤はStep8-dで実装済み | 2026-07-11の情報フロー転換でAI整理が「人間の手動起動」に変わったため、「何が完了したら鳴らすか」の再設計が必要（現状の実装は転換前の設計のまま） |
| データ管理 | エクスポート・アカウント削除UIは未実装 | Integrationsの「Export」と役割が重なるため、実装時にどちらに置くか判断 |

## 4. ② Knowledge（知識）※最重要セクション

Lumoraらしさが最も出る場所。3つの項目を持つ。

### 4-1. Marker（マーカーの意味登録）※今回の直接のきっかけ

**最も守るべき前提**：この機能は「AIのための機能」ではなく「**ユーザー自身の思考ルールを言語化・表現する機能**」である。すでに無意識に使い分けている色の運用ルールを、本人が自覚し言葉にして残すことが第一の目的で、AIと意味を共有できることは副次的な結果に過ぎない。UIの文言・導線（画面タイトル、説明文、コールドスタート時の誘導コピー等）は一貫してこの前提に立って書くこと。「AIに教える」「AIのために設定する」といった言い回しにしない（詳細：VISION.md「1-1」）。

- 5色（ピンク/グリーン/イエロー/ブルー/レッド）それぞれに、ユーザーが**名前と説明を登録できる**
- **任意**。未設定でも色そのものは今まで通り使える（強制しない）
- 初期プリセット案（ピキさんの例をそのまま採用。あくまで初期値でユーザーが変更可能）：

  | 色 | プリセット名 |
  |---|---|
  | 🟨 イエロー | 根拠 |
  | 🟦 ブルー | 仕様 |
  | 🟩 グリーン | 設定 |
  | 🩷 ピンク | アイデア |
  | 🟥 レッド | 注意点 |

- 編集可能項目：色（既存5色から選び直す想定は無い＝色自体は固定、意味づけのみ変更）、名前、説明
- **Phase1のスコープ確認済み（2026-07-13）**：登録UIとデータ保存のみ。`organize-markers`/`organize-wings`のAIプロンプトへ実際に渡すのはPhase2（Beacon設計時）に回す
- データモデル：`data-model.md`「MarkerColorMeaning」参照

### 4-2. AI整理（説明画面）

- Wing/Tag/Summaryを**AIがどう作っているか**を人間に説明する読み物画面（「AIが何をしているか分からない」という不安を減らす）
- 実データを書き換えるものではないため実装コストは低い（静的コンテンツ）
- 将来的に「AIへの指示（プロンプトの一部）をユーザーがカスタマイズする」方向に発展しうるが、Phase1は読み物に留める

### 4-3. Search（検索対象ON/OFF）

- ChatGPT/Claude/Gemini/Perplexityごとに、横断検索の対象に含めるかON/OFFで選べる
- 実装には`search_conversations` RPCへの`sources`フィルタ引数追加が必要（DB層の軽い変更）
- 設定の保存先はDB（`user_settings`的な新テーブル）かAsyncStorage（端末ローカル）か要判断：検索範囲というクエリ挙動そのものに関わるため、複数端末で使うならDB保存が望ましい

## 5. ③ Integrations（接続）

**現状のLumoraのインポートは「エクスポートファイルの手動アップロード」方式のみ**（VISION.md Non-goals「各AI公式アプリとのリアルタイム同期は技術的に不可能」）。この前提とIntegrationsという名称がやや矛盾するため、着手前に意図の確認が必要。

| 項目 | 現状 | 判断 |
|---|---|---|
| AI APIキー | 未実装。ライブ同期基盤は無い | 「各社が対話ログAPIを提供した場合の受け口」なのか、「Lumora自身のAI呼び出しにユーザー自身のAPIキーを使う」なのか、意図の確認が必要（未決定事項参照） |
| Import | `/import`画面が既存 | 新規機能ではなく、設定内にも導線を複製するだけ |
| Export | 未実装 | VISION.md「🚀 知識活用」の柱（MD/仕様書/SNS/翻訳への展開）と関係が深い。Knowledgeセクションが育ってから着手するのが自然 |

## 6. ④ Guide（ガイド）

単なるFAQではなく、**物語として読めるオンボーディング**。ピキさん案をベースにした章立て：

| 章 | タイトル | 内容の骨子 |
|---|---|---|
| 第1章 | Lumoraとは？ | AIとの会話を保存する場所ではない。未来の自分へ残したい一文を育てるナレッジOS |
| 第2章 | 最初にやること | ①AIチャットをインポート ②検索する ③マーカーを引く。たったこれだけ |
| 第3章 | Markerとは？ | 本にマーカーを引く感覚。色の意味はあなた自身が決める（4-1と対になる説明） |
| 第4章 | Realmとは？ | プロジェクト（例：古着ダンジョン、おかわり帳、Lumora） |
| 第5章 | Wingとは？ | AIが整理した知識のカテゴリ（例：ゲームデザイン、UI、技術スタック、世界観） |

About Lumora / Feedbackは静的コンテンツで実装コストは低い。

### 6-1. Guideの検索統合（差別化アイデア、Phase2以降）

検索窓に「Wing」と入力すると、実際の検索結果に加えて「Wingとは？」「Wingの作り方」「AI整理との違い」といったGuideの該当章も一緒に出てくる、というアイデア。**ヘルプ自体がLumoraの検索対象になる**という発想はLumoraならではの差別化になりうる。

実装上の論点：会話検索（DB/RPC）とGuide検索（静的コンテンツ）は別インデックスになるため、`search.tsx`の結果表示（現状は会話行のみ）にGuide行という異なる見た目を混在させる設計が必要。Phase1では章立てガイドの画面を先に作り、検索統合はGuideコンテンツ自体が十分に育ってから着手する。
