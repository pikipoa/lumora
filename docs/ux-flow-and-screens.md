# UXフロー & 画面遷移仕様書（Phase 1）

Knowledge OS — AIチャット統合ナレッジアプリ

前提：`data-model.md` のTag / Summary / Marker が持つ `status: proposed | confirmed | rejected` を、実際の画面操作でどう遷移させるかを定義する。

---

## Part 1. 「AI提案→人間確定」のUXフロー

### 1-1. 共通原則

3つの対象（Tag / Summary / Marker）はすべて同じ状態遷移パターンに従う。

```
[AI生成] proposed ──人間が承認──> confirmed
                └──人間が却下──> rejected（削除ではなく記録として残す）
                └──人間が編集して確定──> confirmed（Summaryのみ status="edited"のニュアンスも持つ）

[人間が手動作成] ──常に──> confirmed（提案フローを経ない）
```

**UI上の視覚原則**：
- `proposed`：破線ボーダー／薄い色／「AI提案」ラベル付きで表示。「まだ確定していない」ことが一目でわかる
- `confirmed`：実線ボーダー／通常の色。他の確定情報と見分けがつかない（＝一度確定したらAI由来か人間由来かをUI上で区別しすぎない。判断者はピキさんであり、由来はデータ上残れば十分）
- `rejected`：デフォルトでは非表示。「却下履歴を見る」を開いた時だけ表示（誤操作の見直し・BAS的な判断履歴の参照用）

### 1-2. タグのフロー

**0. タグ提案の前提ロジック（スコープ判定と既存優先マッチング）**

タグの野放図な増殖（例：「#雑談です」「#今日の天気の話」のような使い捨てタグ）を防ぐため、AIのタグ提案は2段階の判定を経る。

```
Step1（スコープ判定）：
  この会話に「後で参照したくなる意思決定・仕様検討・設計判断・アイデア」が
  含まれているか判定する。純粋な世間話・雑談・プロジェクトと無関係な内容のみの場合、
  タグ提案自体をスキップする（提案タグ0件のままでよい）。
  ※試行錯誤やトラブルシューティングの過程は、結論が出ていなくても対象に含める
  （AI Survival Kitの成り立ちと同様、プロセス自体に資産価値があるため除外しない）

Step2（既存優先マッチング）：
  Step1を通過した会話について、以下の優先順位でタグを決める：
  ① 同じプロジェクト内で既に使われているタグから合うものを探す
  ② 見つからなければ、他プロジェクトも含めた全体のタグ一覧から探す
     （#AI #ClaudeCodeのような複数プロジェクト共通タグの再利用を想定）
  ③ ①②どちらにも当てはまらない場合のみ、新規タグを提案する
```

**コールドスタート（最初はタグが1つもない問題）への対応**：
- プロジェクト作成時に、人間側が任意で「種タグ」を先に登録できるようにする（例：`#UI #世界観 #実装 #課金 #未解決課題`のような、ピキさんが過去のプロジェクトで実際に使っていたタグ体系をテンプレとして最初から用意）
- 種タグを登録しない/最初のインポート時点で該当タグが無い場合は、Step2の①②が自然にゼロ件になり、③（新規提案）に自動フォールバックする。専用のコールドスタート処理は不要で、優先順位ロジック1本で空の状態からも立ち上がる設計とする

1. インポート＆AI処理が完了すると、会話ごとに0〜N個のタグが`proposed`状態で自動生成される
2. 会話詳細画面のタグエリアに、提案タグが破線チップで並ぶ
   例：`⟨UI設計⟩ proposed` `⟨闘着場⟩ proposed`
3. 各チップをタップ → **承認／却下**の2択が出る（編集ではなく承認/却下のみ。タグ名自体を直す場合は却下→自分で新規追加が自然）
4. 「＋タグを追加」ボタンで人間が手動追加 → 即`confirmed`
5. 一括承認ボタンはPhase1では設置しない（論点E参照）。1件ずつタップして承認/却下する運用とする

### 1-3. 要約のフロー

1. AI要約が`proposed`状態で1件生成される（会話ごとに1件、Phase1は上書き運用）
2. 会話詳細画面の上部に「AI要約（未確定）」として表示。以下の3アクション：
   - **このままでOK** → `confirmed`
   - **編集する** → テキスト編集モードに入り、保存すると`edited`（＝人間が手を加えた確定版）
   - **不要（非表示にする）** → `rejected`。以後その会話には要約が表示されない
3. `confirmed`/`edited`になった要約は通常表示（破線が取れる）

### 1-4. マーカー（重要箇所抽出）のフロー

これが最も操作頻度が高くなる想定なので、UIの摩擦を最小にする設計にする。

**重要な前提**：AIが提案するのは「だいたいこのあたりが重要」という**近似的な範囲**であり、人間が最終的に採用する範囲は必ずしも一致しない。そのため、マーカーレビューは単純な承認/却下の2択ではなく、**「提案範囲を自分で微調整してから確定する」**という一手間が入る。

1. AIが重要と判断した文章に、メッセージ本文中で**薄いハイライト**がかかる（`proposed`状態、この時点の`quoted_text`はAIの近似的な提案、`color: null`）
2. ハイライト部分をタップ（または選択）すると、**テキスト選択ハンドル（ドラッグで範囲を伸縮できるUI、スマホのコピー操作と同じ見た目）**が出る
3. 範囲を調整すると、選択範囲の上部または下部に**マーカー色選択バー**が出る。これはOS標準の「コピー／切り取り／貼り付け」メニューの代わりにアプリ内で独自表示するもの：

   ```
   [🩷] [💚] [💛] [💙] [❤️]
   蛍光ピンク 蛍光グリーン 蛍光イエロー 蛍光ブルー レッド
   ```

   **色をタップする行為そのものが確定操作を兼ねる**（「範囲調整→色を選ぶ」の2ステップで完結し、別途「OK」ボタンを押す必要がない）。タップした色が`Marker.color`に入り、同時に`status: confirmed`になる
4. 範囲を全く採用したくない場合は、色バーの外側をタップするか「却下」で`rejected`
5. **ハイライトされていない文章も、人間が任意に選択してマーカーを引ける**（テキスト選択→同じ色選択バーが出現→色をタップで即`confirmed`）。この場合`proposed_by: human`

**色の意味づけについて**：Phase1では色ごとの意味（例：ピンク＝要仕様化、グリーン＝実装候補）はシステム側で固定しない。あくまで「本にマーカーを引く」体験の再現が目的であり、意味づけは人間側が運用の中で決める。色ごとの凡例機能（レジェンド表示）は将来の拡張候補としてバックログに置く。

**デバイス別の操作方式（決定）**：
ピキさんの実態は「Claude Code作業＝PC」「それ以外のAIとのやり取り＝ほぼスマホ（PCでの文字入力が遅いため）」とのことなので、マーカーレビューもこの使い分けに合わせて最適化する。

- **スマホ**：カードスワイプ式のレビューモード。1件ずつカードで提示し、まず範囲調整ハンドルで微調整→右スワイプで確定／左スワイプで却下。範囲調整とスワイプ確定を1カードの中で完結させる
- **PC**：一覧型のキーボードショートカット式。候補を上から並べ、`j`/`k`（または矢印キー）で候補間移動、`Shift+矢印`で選択範囲を伸縮、`Enter`で確定、`Backspace`または`X`で却下。範囲調整はドラッグでも可能だが、キーボードでも完結できるようにする

**共通のバックエンド仕様**：入力方式（スワイプ or キーボード）が違うだけで、確定時に呼ぶAPI（`quoted_text`更新＋`status: confirmed`への変更）は共通。フロントエンドのみデバイス判定で出し分ける設計とする。

### 1-5. なぜこの設計か（哲学の再確認）

「受付カウンターUI」（AI視点）と「闘着場という世界観の入口設計」（作者視点）の差分を残すのが目的。そのため：
- **承認は「AIの言葉をそのまま採用する」ことも意味する**が、タグは却下→再入力によって作者独自の意味づけに置き換えられる
- **却下履歴を残す**のは、「AIはこう見たが、自分はそう思わなかった」という判断そのものが将来の資産になるため（BASのCross-Path Resistance思想と同型）

## Part 2. 画面遷移・ワイヤーフレームレベル

### 2-1. 画面一覧

| # | 画面名 | 役割 |
|---|---|---|
| S1 | インポート画面 | ファイルアップロード、形式自動判定 |
| S2 | インポート完了サマリー | 成功/失敗件数、レビューへの導線 |
| S3 | プロジェクト一覧 | Project一覧（＋未分類Inbox） |
| S4 | プロジェクト詳細 | Theme一覧、プロジェクト内会話数、未レビュー件数 |
| S5 | 会話一覧（Theme内 or Inbox） | Conversationのリスト表示 |
| S6 | 会話詳細（レビュー画面） | 本体。要約/タグ/マーカーのAI提案を確認・確定する主戦場 |
| S7 | マーカーレビューモード | S6内のサブモード。proposedマーカーをカード形式で連続承認/却下 |
| S8 | 横断検索画面 | 全プロジェクト・全AI横断のキーワード/タグ検索 |
| S9 | 重要部分だけ表示画面 | confirmedマーカーのみを一覧表示（プロジェクト内 or 全体） |

### 2-2. 画面遷移図（テキスト）

```
S1 インポート画面
   └─(アップロード完了)→ S2 インポート完了サマリー
                              ├─(レビューを始める)→ S6 会話詳細（未分類の先頭から）
                              └─(後で)→ S3 プロジェクト一覧

S3 プロジェクト一覧
   ├─(プロジェクトをタップ)→ S4 プロジェクト詳細
   ├─(未分類Inboxをタップ)→ S5 会話一覧（Inbox）
   └─(グローバルナビ)→ S8 横断検索 / S9 重要部分だけ表示

S4 プロジェクト詳細
   └─(Themeをタップ)→ S5 会話一覧（Theme内）

S5 会話一覧
   └─(会話をタップ)→ S6 会話詳細

S6 会話詳細（レビュー画面）
   ├─(タグ提案を承認/却下)→ 同画面内で即時更新
   ├─(要約を確定/編集/却下)→ 同画面内で即時更新
   ├─(マーカーを複数まとめてレビュー)→ S7 マーカーレビューモード
   ├─(未分類の場合：プロジェクト/テーマを割当)→ 同画面内モーダル
   └─(戻る)→ S5 会話一覧

S7 マーカーレビューモード
   └─(全件終了 or 途中終了)→ S6 会話詳細に戻る

S8 横断検索
   └─(結果の会話をタップ)→ S6 会話詳細

S9 重要部分だけ表示
   └─(マーカーをタップ)→ S6 会話詳細（該当箇所にジャンプ）
```

### 2-3b. S7 マーカーレビューモード（デバイス別）

```
│   ◉━━ドラッグで範囲調整━━◉      │
```

```
│  ✓ 「候補文章1」                │
│  → 「候補文章2」  ← 選択中      │
│     Shift+←/→ で範囲調整       │
│  ・ 「候補文章3」               │
│                               │

```
一覧から矢印/jk移動、Shift+矢印で範囲伸縮、数字キー1〜5で色を選ぶと同時に確定。

### 2-4. 未レビュー状態の可視化

S3〜S5の一覧画面では、各Project/Theme/Conversationに**未レビュー件数バッジ**を表示する（例：「闘着場 (3件レビュー待ち)」）。これにより「インポートしたが放置」を防ぐ。

## 3. 次に詰めるべき論点（要判断）

- ~~論点D：マーカーレビューのスワイプ式 vs キーボード式~~ → **決定済み**：デバイス判定でスマホ=スワイプ+範囲調整+色選択、PC=キーボードショートカット+範囲調整+数字キー色選択。バックエンドAPIは共通
- ~~論点E：「すべて承認」ボタン~~ → **決定済み：Phase1では実装しない**。AI提案の精度が未検証な段階での一括承認は誤確定を量産するリスクがあるため、1件ずつの確認を必須とする
