## Part 1. 「AI提案→人間確定」のUXフロー（旧設計。2026-07-11更新版は各節参照）

### 1-1. 共通原則

> **2026-07-11更新**：転換後は「AIが最初に生成し、人間が確認する」という関係にあるのは**MarkerTagのみ**。Markerは常に人間が手動作成し、作成と同時にconfirmed（Arca）になる（proposedを経由しない）。ConversationTagはAI提案の生成元（会話全体のAI処理）が無くなったため、実質的に人間の手動追加＝即confirmedのみが発生する（状態遷移の仕組み自体はコード上残っているが、AIがproposedを作ることはない）。Summaryは機能自体を廃止した。

以下は転換前の3対象（Tag / Summary / Marker）共通の状態遷移パターン（**Summaryは廃止済み、Markerは現在は該当しない**。MarkerTagにのみ引き続き適用される）。

```
[AI生成] proposed ──人間が承認──> confirmed
                └──人間が却下──> rejected（削除ではなく記録として残す）
                └──人間が編集して確定──> confirmed（Summaryのみ status="edited"のニュアンスも持つ。廃止済み）

[人間が手動作成] ──常に──> confirmed（提案フローを経ない）
```

**UI上の視覚原則**：
- `proposed`：破線ボーダー／薄い色／「**Ore**」ラベル付きで表示。「まだ精錬（確定）されていない」ことが一目でわかる
- `confirmed`：実線ボーダー／通常の色。他の確定情報と見分けがつかない（＝一度確定したらAI由来か人間由来かをUI上で区別しすぎない。判断者はピキさんであり、由来はデータ上残れば十分）。UI上は「**Arca**に収録済み」という扱い
- `rejected`：デフォルトでは非表示。「却下履歴を見る」を開いた時だけ表示（誤操作の見直し・BAS的な判断履歴の参照用）

### 1-2. タグのフロー（ConversationTag / MarkerTag共通パターン）

**役割分担の再確認**：
- `MarkerTag`（主戦場）：個々の発見物（Marker）単位。会話内でトピックが混ざっても正確にタグ付けできる
- `ConversationTag`（補助）：会話（Chronicle）全体への大まかな分類。横断検索の粗い絞り込みに使う
- どちらもTopic/Conceptの2種類のみ対象（Roleは対象外、後述1-4参照）

**0. タグ提案の前提ロジック（スコープ判定と既存優先マッチング）**

タグの野放図な増殖（例：「#雑談です」「#今日の天気の話」のような使い捨てタグ）を防ぐため、AIのタグ提案は2段階の判定を経る。

```
Step1（スコープ判定）：
  MarkerTagの場合：Markerは既に「重要箇所」として選別済みのため、この判定は
  実質的に省略できる（マーカー化された時点で「タグ付けする価値がある」とみなす）。

  ConversationTagの場合：この会話に「後で参照したくなる意思決定・仕様検討・
  設計判断・アイデア」が含まれているか判定する。純粋な世間話・雑談・
  プロジェクトと無関係な内容のみの場合、タグ提案自体をスキップする。
  ※試行錯誤やトラブルシューティングの過程は、結論が出ていなくても対象に含める
  （AI Survival Kitの成り立ちと同様、プロセス自体に資産価値があるため除外しない）

Step2（既存優先マッチング）：
  Step1を通過した対象（Marker or Conversation）について、以下の優先順位でタグを決める：
  ① 同じプロジェクト内で既に使われているタグから合うものを探す
  ② 見つからなければ、他プロジェクトも含めた全体のタグ一覧から探す
     （#AI #ClaudeCodeのような複数プロジェクト共通タグの再利用を想定）
  ③ ①②どちらにも当てはまらない場合のみ、新規タグを提案する
```

**コールドスタート（最初はタグが1つもない問題）への対応**：
- プロジェクト作成時に、人間側が任意で「種タグ」を先に登録できるようにする（例：`#UI #世界観 #実装 #課金 #未解決課題`のような、ピキさんが過去のプロジェクトで実際に使っていたタグ体系をテンプレとして最初から用意）
- 種タグを登録しない/最初のインポート時点で該当タグが無い場合は、Step2の①②が自然にゼロ件になり、③（新規提案）に自動フォールバックする。専用のコールドスタート処理は不要で、優先順位ロジック1本で空の状態からも立ち上がる設計とする

**ConversationTagのUIフロー（2026-07-11更新：AI自動生成は廃止）**：
1. ~~インポート＆AI処理が完了すると、会話ごとに0〜N個のタグが`proposed`（Ore）状態で自動生成される~~ → 廃止。会話全体を分析するAI処理自体が無くなったため、ConversationTagがAIによって`proposed`状態で生成されることはない
2. 会話詳細画面（S6）のタグエリアでは、人間が「＋タグを追加」ボタンで手動追加したタグのみが並ぶ → 追加と同時に`confirmed`（Arca）
3. 過去の転換前データに`proposed`状態のConversationTagが残っている場合のみ、承認／却下のチップ操作UIが引き続き機能する（新規に発生することはない）

### 1-3. 要約のフロー → 廃止（決定・2026-07-11）

~~AI要約が`proposed`状態で1件生成される～confirmed/edited/rejectedの3アクション～~~

会話単位のAI要約（Summary）機能は情報フローの転換に伴い完全廃止した。`summaries`テーブルも物理削除済み。理由：知識の最小単位が「会話」から「マーカー」に変わったため、会話全体を要約する必然性が無くなった（詳細：`VISION.md`「3-3」）。以下は歴史的記録として残す（本文は元のまま）：

> 1. AI要約が`proposed`状態で1件生成される（会話ごとに1件、Phase1は上書き運用）
> 2. 会話詳細画面の上部に「AI要約（未確定）」として表示。以下の3アクション：
>    - **このままでOK** → `confirmed`
>    - **編集する** → テキスト編集モードに入り、保存すると`edited`（＝人間が手を加えた確定版）
>    - **不要（非表示にする）** → `rejected`。以後その会話には要約が表示されない
> 3. `confirmed`/`edited`になった要約は通常表示（破線が取れる）

### 1-4. マーカー（重要箇所抽出）のフロー

#### 2026-07-11更新：現在の正式フロー

マーカーは**常に人間が能動的に作る**。AIが「ここが重要」と近似範囲を提案することはない（旧フローは本節末尾に記録として残す）。

1. 人間が横断検索（S8）または会話一覧（Inbox、フォールバック用）から会話を開く
2. 会話本文中の任意の文章を**選択**する（テキスト選択ハンドル、スマホのコピー操作と同じ見た目のドラッグUI）
3. 範囲を調整すると、選択範囲の上部または下部に**マーカー色選択バー**が出る：

   ```
   [🩷] [💚] [💛] [💙] [❤️]
   蛍光ピンク 蛍光グリーン 蛍光イエロー 蛍光ブルー レッド
   ```

   **色をタップする行為そのものが確定操作を兼ねる**（「範囲選択→色を選ぶ」の2ステップで完結）。タップした色が`Marker.color`に入り、同時に`status: confirmed`・`proposed_by: human`になる（＝Arcaへ追加）。proposed状態を経由しない
4. 色選択で確定した直後、続けて**Roleタグ選択**が表示される（任意項目、スキップ可）：
   ```
   💡idea  🔭hypothesis  📌decision  ⚔️strategy  📚learning
   ```
   何も選ばずスキップも可能（`role_tag: null`のまま確定できる）
5. マーカー確定の時点ではMarkerTag（Topic/Concept）は**まだ付かない**。タグ付けはArca画面（旧S9）から人間がまとめて「タグを整理する」を起動した時に初めてAIが提案する（1-2節参照）。作成直後の連続タグレビューは行わない（バッチ整理に変わったため）
6. Realm（プロジェクト）への割り当ても作成時には必須ではなく、Arca画面から後でまとめて行う（`markers.project_id`）

#### 旧フロー（2026-07-10まで採用、記録として保持）

これが最も操作頻度が高くなる想定なので、UIの摩擦を最小にする設計にする、としていた。

**旧・重要な前提**：AIが提案するのは「だいたいこのあたりが重要」という**近似的な範囲**であり、人間が最終的に採用する範囲は必ずしも一致しない。そのため、マーカーレビューは単純な承認/却下の2択ではなく、**「提案範囲を自分で微調整してから確定する」**という一手間が入る、としていた。

> 1. AIが重要と判断した文章に、メッセージ本文中で**薄いハイライト**がかかる（`proposed`状態、この時点の`quoted_text`はAIの近似的な提案、`color: null`）
> 2. ハイライト部分をタップ（または選択）すると、テキスト選択ハンドルが出る
> 3. 範囲を調整すると色選択バーが出て、色をタップする行為そのものが確定操作を兼ねる
> 4. 範囲を全く採用したくない場合は「却下」で`rejected`
> 5. ハイライトされていない文章も、人間が任意に選択してマーカーを引ける（この場合`proposed_by: human`）
> 6. 色選択で確定した直後、続けてRoleタグ選択が表示される
> 7. マーカー確定（色選択）の直後、AIが提案するTopic/Conceptタグ（MarkerTag、`proposed`＝Ore状態）が同じ画面内に表示される

このうち5（人間による任意選択→即confirmed）の部分だけが、2026-07-11更新版の唯一のパスとして残り、1〜4・7（AIによる自動発見・自動タグ即時提案）は廃止された。

**色の意味づけについて**：Phase1では色ごとの意味（例：ピンク＝要仕様化、グリーン＝実装候補）はシステム側で固定しない。あくまで「本にマーカーを引く」体験の再現が目的であり、意味づけは人間側が運用の中で決める。色ごとの凡例機能（レジェンド表示）は将来の拡張候補としてバックログに置く。

**デバイス別の操作方式（決定）**：
ピキさんの実態は「Claude Code作業＝PC」「それ以外のAIとのやり取り＝ほぼスマホ（PCでの文字入力が遅いため）」とのことなので、マーカーレビューもこの使い分けに合わせて最適化する。

- **スマホ**：カードスワイプ式のレビューモード。1件ずつカードで提示し、まず範囲調整ハンドルで微調整→右スワイプで確定／左スワイプで却下。範囲調整とスワイプ確定を1カードの中で完結させる
- **PC**（Expo Webビルドをブラウザで利用。詳細：`CLAUDE.md`）：一覧型のキーボードショートカット式。候補を上から並べ、`j`/`k`（または矢印キー）で候補間移動、`Shift+矢印`で選択範囲を伸縮、`Enter`で確定、`Backspace`または`X`で却下。範囲調整はドラッグでも可能だが、キーボードでも完結できるようにする

**共通のバックエンド仕様**：入力方式（スワイプ or キーボード）が違うだけで、確定時に呼ぶAPI（`quoted_text`更新＋`status: confirmed`への変更）は共通。フロントエンドのみデバイス判定で出し分ける設計とする。

### 1-5. なぜこの設計か（哲学の再確認）

「受付カウンターUI」（AI視点）と「闘着場という世界観の入口設計」（作者視点）の差分を残すのが目的。そのため：
- **承認は「AIの言葉をそのまま採用する」ことも意味する**が、タグは却下→再入力によって作者独自の意味づけに置き換えられる
- **却下履歴を残す**のは、「AIはこう見たが、自分はそう思わなかった」という判断そのものが将来の資産になるため（BASのCross-Path Resistance思想と同型）
