# start_offset バックフィル

2026-07-26のマーカー位置ズレ調査（`CHANGELOG.md`参照）で`markers`に
`start_offset`/`end_offset`を追加した。マイグレーション前に作成された既存マーカーは
これが`null`で、表示時は`quoted_text`の`indexOf`にフォールバックする。同じ文字列が
本文中に複数回出現する場合、常に**最初の一致**に解決されるため位置ズレが残る。

## 安全条件をTierで分ける

SQLだけで安全に確定できるのは「出現が1回だけ」のものに限られる。

| Tier | 条件 | 扱い |
|---|---|---|
| **Tier 1** | 本文中に**ちょうど1回**出現 | 位置が一意に定まる。**自動確定してよい** |
| **Tier 2** | 複数回出現 | SQLでは確定不能。周辺文脈からの**推定**が必要 |
| **Tier 3** | 本文中に見つからない | **保留**。本文が編集された・再インポートされた等の可能性 |

## 実行手順

1. `01_survey_marker_offsets.sql` を実行して現状を把握する（**読み取りのみ・変更なし**）
   - Tier別の件数
   - Tier 2 が何回出現するマーカーなのかの内訳（2回程度なら推定の効果が高い）
   - Tier 3 のサンプル20件
   - 既存`start_offset`の健全性チェック
2. Tier 1 の件数を確認した上で `02_backfill_tier1.sql` を実行する
   - 末尾の検証クエリ `inconsistent_after_backfill` が **0 であることを確認してから commit**
   - 0 でなければ rollback

## Tier 2 に着手する場合の設計メモ（未実装）

複数回出現するマーカーの位置を文脈から**推定**する場合、確定分と推定分を後から区別
できないと危険。「なぜこの位置なのか」を誰も説明できないデータが混ざる。

着手するなら、推定であることをデータに残す仕組みを先に用意すること。案：

- `markers`に`offset_source`列を追加（`'user'` / `'backfill_exact'` / `'backfill_inferred'`）
- 推定分は表示時に確度を落とすか、ユーザーに確認を促す導線を用意する

Lumoraの設計原則（`PRINCIPLES.md`：AIは提案者であり決定者ではない／知識は破壊しない）に
照らしても、推定値を確定値と同じ顔で保存するのは避けるべき。

## Tier 3 について

本文に`quoted_text`が見つからないもの。元の位置はデータから復元できない。
`indexOf`フォールバックも効かないため、そもそも画面に表示されていない可能性が高い。
件数を把握した上で、放置するか個別に対応するかを判断する。
